Module 3 · RAG Done Right

RAG Done Right

Module 2 was about whether you can trust what the model says. This module is about whether the model was ever shown the right material. Retrieval is where most RAG systems quietly fail, and it's the one part you can measure without calling a model at all, so that's what you'll do: start from the simplest possible pipeline, score it, and improve it one change at a time, keeping only what the score justifies.

The labs share one answer key. A script generates fake product manuals as real PDFs, with tables, near-duplicate pages and a few image-only scans, and labels the exact page that answers each question. Because you know the right answer, every lab can report a number instead of an impression. Your numbers will differ from any quoted here, because they depend on the corpus the generator produces and the embedding model, so the checks tell you what to look for and ask you to record your own.

Concepts

Two halves, and the retrieval half decides everything

A RAG system (retrieval-augmented generation, the pattern named in Lewis et al.'s 2020 NeurIPS paper Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks) has an indexing half that runs once per document and a query half that runs on every question. The model only ever sees what retrieval hands it. If the right passage isn't in the top few results, no prompt can recover it, and the model will either say it can't find the answer or answer from the wrong passage.

That's why this module measures retrieval on its own, before any model is involved. Every lab scores recall@k: for each labeled question, did the correct page show up in the top k retrieved chunks? It's a plain pass/fail count you can compute in milliseconds and re-run after every change, which is exactly what makes it possible to improve a pipeline on evidence instead of vibes.

Parsing: most failures start before the embedding

A PDF isn't text. It's drawing instructions that happen to place glyphs on a page. A basic extractor like pypdf reads those glyphs back in drawing order, which is fine for a paragraph and ruinous for a table: every cell lands on its own line and the row structure disappears. A layout-aware parser (pymupdf4llm here; Docling, LlamaParse and Microsoft's markitdown are the same idea) detects the table and emits a real Markdown table. Lab 2 shows you the difference on your own screen.

A scanned PDF is worse: it's a stack of page images with no text layer at all, so a text extractor returns an empty string and the document is silently invisible to search. Scans need OCR (optical character recognition). Classic OCR engines like Tesseract work; so does sending a picture of the page to a vision-capable model and asking for a Markdown transcription, which also handles tables. Either way, check for empty pages explicitly. A pipeline that quietly indexes nothing looks exactly like one that works.

Chunking: the unit of retrieval

You can't embed a 200-page manual as one vector; the vector would be a blurry average of everything in it. So documents get cut into chunks, and each chunk is embedded and retrieved on its own. Cut too small and a chunk loses the surrounding meaning; cut too large and one vector has to represent several unrelated ideas, so none of them match a question well.

Three choices matter. Size (characters or tokens per chunk). Overlap, repeating the tail of one chunk at the start of the next so a fact straddling a boundary survives in at least one piece. And boundaries: splitting on the document's own structure (headings, paragraphs, whole tables) instead of every N characters. The strategy that works best depends on the document type, which is why Lab 3 compares them instead of recommending one.

Context: a chunk has to say where it came from

Take a specs table that lists pressure, cable length and part number but never names the product. Once it's cut out of its page, a human couldn't tell whose specs they are, and neither can an embedding model. The fix is cheap: prepend a short context line (document title, section, page) to every chunk before embedding it. Anthropic described a more elaborate variant of the same idea, having a model write each chunk's context, in its September 2024 post Introducing Contextual Retrieval. Lab 3 uses the simple, free version, built from the file name, and measures what it buys.

Vector indexes: HNSW, IVF and PQ

Finding the nearest vectors by comparing a question against every stored chunk is exact and simple, and it's fine up to tens of thousands of chunks. Beyond that you want an approximate nearest neighbor index, which trades a little accuracy for a lot of speed. Three names come up constantly:

HNSW (Malkov and Yashunin, Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs, IEEE TPAMI, 2018) links each vector to its neighbors in layered graphs and searches by hopping along links. It's fast and accurate and keeps the full vectors in memory plus the links. IVF (inverted file) clusters the vectors up front and, at query time, only scans the few clusters nearest the question; the nprobe setting is how many it checks. PQ (product quantization; Jégou, Douze and Schmid, IEEE TPAMI, 2011) compresses each vector into a short code, shrinking memory by an order of magnitude while making distances approximate. IVF and PQ are usually combined as IVF-PQ. Lab 4 builds both and measures the trade, using Meta's open-source Faiss library (Johnson, Douze and Jégou, Billion-scale similarity search with GPUs, IEEE Transactions on Big Data, 2019).

Hybrid search: meaning plus exact words

Embeddings match meaning, which is why "how long is the guarantee" can find a passage about the "warranty period". They are weaker on exact strings: part numbers, error codes, names, IDs. Keyword search with BM25 (the ranking function surveyed in Robertson and Zaragoza, The Probabilistic Relevance Framework: BM25 and Beyond, Foundations and Trends in Information Retrieval, 2009) is the opposite: blind to paraphrase, excellent on exact terms.

Hybrid search runs both and merges the two ranked lists. The merge that's become the default is reciprocal rank fusion (Cormack, Clarke and Büttcher, SIGIR 2009): each list gives every result a score of 1/(60 + rank), and you sum across lists. It only uses ranks, so you never have to reconcile BM25's score scale with cosine similarity's, and a chunk that both lists like rises to the top.

Question handling: split it, then filter it

Real questions are often two questions glued together ("compare the warranty on the Aster Probe and the Delta Sensor"). A single search for the whole sentence tends to find neither. The standard move is to have a model split a multi-part question into sub-questions, retrieve for each, and merge. Separately, many questions carry a metadata filter in plain sight: a product, a date range, a document type. Restricting the search to chunks whose metadata matches removes whole classes of near-identical distractors before ranking even starts. Lab 6 does the filter half with a simple rule; in production a model extracts the filter values from the question.

Reranking: a second, slower, smarter look

Embedding search scores a chunk and a question separately and then compares the vectors, which is fast but coarse. A cross-encoder reranker reads the question and one chunk together and outputs a relevance score, which is far more precise and far too slow to run over every chunk. So the standard shape is two stages: cheap retrieval pulls a pool (top 20), the reranker re-orders just that pool, and you keep the top 5. You pay latency on every query, so Lab 6 measures both what you gain and what it costs.

  4. Create rag/common.py, the helpers every later lab imports: a page loader, an embedder that caches every vector on disk (so re-running a lab doesn't re-bill you), cosine search, and the recall_at_k scorer.
    import hashlib, json, os from pathlib import Path import numpy as np import pypdf from dotenv import load_dotenv load_dotenv() CACHE = Path("rag/.embed_cache"); CACHE.mkdir(exist_ok=True) def load_pages(corpus="rag/corpus"): """Naive parser: one (doc, page_number, text) per PDF page.""" pages = [] for pdf in sorted(Path(corpus).glob("*.pdf")): for n, page in enumerate(pypdf.PdfReader(pdf).pages, start=1): pages.append({"doc": pdf.name, "page": n, "text": page.extract_text() or ""}) return pages def embed(texts, model="text-embedding-3-small"): """Embed a list of strings, caching each one on disk so re-runs cost nothing.""" from openai import OpenAI client = OpenAI(api_key=os.environ["OPENAI_API_KEY"]) out, todo = {}, [] for t in texts: f = CACHE / (hashlib.sha256((model + t).encode()).hexdigest() + ".json") if f.exists(): out[t] = json.loads(f.read_text()) else: todo.append((t, f)) for i in range(0, len(todo), 100): batch = todo[i:i + 100] resp = client.embeddings.create(model=model, input=[t for t, _ in batch]) for (t, f), d in zip(batch, resp.data): f.write_text(json.dumps(d.embedding)); out[t] = d.embedding return np.array([out[t] for t in texts], dtype="float32") def top_k_vector(q_vec, chunk_vecs, k): """Cosine similarity via normalized dot product; returns chunk indexes, best first.""" a = chunk_vecs / np.linalg.norm(chunk_vecs, axis=1, keepdims=True) b = q_vec / np.linalg.norm(q_vec) return list(np.argsort(-(a @ b))[:k]) def recall_at_k(questions, retrieve, chunks, k=5): """retrieve(question, k) -> list of chunk indexes. A hit means any of the top k chunks comes from the labeled doc AND one of its labeled pages.""" hits, misses = 0, [] for q in questions: got = [(chunks[i]["doc"], chunks[i]["page"]) for i in retrieve(q["q"], k)] if any((q["doc"], pg) in got for pg in q["pages"]): hits += 1 else: misses.append(q["q"]) return hits / len(questions), misses

Create rag/chunking.py with three chunkers and the context-prefix helper: fixed-size with an optional overlap; a structure-aware chunker that splits on blank lines (so a Markdown table stays whole) and packs neighbors up to a size cap; and add_context, which prepends "From the Larkfield <product> manual, page N:" to every chunk.
    import re def chunk_fixed(pages, size=500, overlap=0): out, step = [], size - overlap for p in pages: for start in range(0, len(p["text"]), step): piece = p["text"][start:start + size].strip() if piece: out.append({"doc": p["doc"], "page": p["page"], "text": piece}) return out def chunk_structure(pages, max_chars=800): """Split on blank lines (paragraphs, headings, whole tables), then pack neighbors together until max_chars. At this module's corpus size (a few hundred chunks), none of this is needed, and an exact search is the right answer. You're building the instinct for when the corpus is a million chunks.

    import json, re from rank_bm25 import BM25Okapi from common import embed, top_k_vector, recall_at_k from parsing import load_pages_md from chunking import chunk_structure, add_context def tokenize(text): return re.findall(r"\w+", text.lower()) pages = load_pages_md() chunks = add_context(chunk_structure(pages, 800)) vecs = embed([c["text"] for c in chunks]) bm25 = BM25Okapi([tokenize(c["text"]) for c in chunks]) questions = json.load(open("rag/questions.json")) def vector_search(q, k): return list(top_k_vector(embed([q])[0], vecs, k)) def keyword_search(q, k): scores = bm25.get_scores(tokenize(q)) return sorted(range(len(chunks)), key=lambda i: -scores[i])[:k] def rrf(rankings, k=60): """Reciprocal rank fusion: each list votes 1/(k+rank) for every chunk it returns.""" fused = {} for ranking in rankings: for rank, i in enumerate(ranking, start=1): fused[i] = fused.get(i, 0) + 1 / (k + rank) return sorted(fused, key=fused.get, reverse=True) def hybrid_search(q, k, pool=20): return rrf([vector_search(q, pool), keyword_search(q, pool)])[:k] if __name__ == "__main__": for name, fn in [("vector", vector_search), ("keyword", keyword_search), ("hybrid", hybrid_search)]: score, misses = recall_at_k(questions, fn, chunks, k=5) print(f"{name:8s} recall@5 = {score:.0%}") # Which questions does fusion rescue? Compare per-question hits. def hit(fn, q): got = [(chunks[i]["doc"], chunks[i]["page"]) for i in fn(q["q"], 5)] return any((q["doc"], pg) in got for pg in q["pages"]) print("\nFixed by hybrid (vector missed, hybrid found):") for q in questions: if not hit(vector_search, q) and hit(hybrid_search, q): print(" ", q["q"])
  2. Run it.
    python rag/hybrid.py
  3. Look at the "Fixed by hybrid" list. Is it the exact-identifier questions ("Which product is part number LK-...?")? If it's something else, work out why keyword search rescued it. Then check the reverse: are there questions vector search found that keyword search missed? Those are the paraphrases hybrid exists to protect.
  4. Try the one fusion knob. Change the k=60 constant in rrf to 10 and then 200 and watch whether anything moves. (It's a smoothing constant from the original paper; on a small corpus it rarely matters, and knowing that saves you from tuning it.)
Check: hybrid should be at least as good as the better of the two single methods on the questions that matter to you, and the part-number question is the textbook case: the embedding model has no reason to treat "LK-2126-B" as meaningful, but BM25 matches the string exactly. This corpus is synthetic and keyword-friendly (every question names the product), so keyword-only may score very well here; don't conclude hybrid is pointless. On real documents with vaguer questions, neither single method wins everywhere, which is the argument for running both.
  1. Create rag/rerank_filter.py. It takes the hybrid pool (top 20), optionally filters it to the product named in the question, then reorders it with a small open cross-encoder, cross-encoder/ms-marco-MiniLM-L-6-v2, and keeps the top 5. The product filter here is a deliberately simple rule (match the product's name in the question). In production you'd have a model extract it.
    import json, re, time from sentence_transformers import CrossEncoder from common import recall_at_k from hybrid import chunks, questions, hybrid_search reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") def product_slug(question): """Stand-in for 'extract the product from the question'. Matches a doc whose name (e.g. 'delta_sensor') appears in the question text.""" q = re.sub(r"[^a-z ]", "", question.lower()) for doc in {c["doc"] for c in chunks}: name = re.sub(r"^\d+_|_scan|\.pdf", "", doc).replace("_", " ") if name in q: return doc return None def retrieve_rerank(q, k, pool=20, use_filter=False): candidates = hybrid_search(q, pool) if use_filter and (doc := product_slug(q)): candidates = [i for i in candidates if chunks[i]["doc"] == doc] or candidates scores = reranker.predict([(q, chunks[i]["text"]) for i in candidates]) return [i for _, i in sorted(zip(scores, candidates), reverse=True)][:k] if __name__ == "__main__": for label, fn in [("hybrid only", hybrid_search), ("hybrid + rerank", retrieve_rerank), ("hybrid + rerank + filter", lambda q, k: retrieve_rerank(q, k, use_filter=True))]: t0 = time.time() score, _ = recall_at_k(questions, fn, chunks, k=5) ms = (time.time() - t0) / len(questions) * 1000 print(f"{label:26s} recall@5={score:.0%} {ms:.0f} ms/question")
  2. Run it. The first run downloads the reranker model (tens of megabytes) and loads PyTorch, so expect a pause.
    python rag/rerank_filter.py
  3. Record both columns for each row: recall@5 and milliseconds per question. The reranker adds latency to every query, and whether the recall gain is worth that is a product decision, not a technical one.
  4. Break the filter on purpose: ask a question that names no product ("What is the warranty period?"). Confirm the code falls back to the unfiltered pool instead of returning nothing. A filter that can silently empty your results is a bug waiting for a user.
Check: expect rerank to help most when the right chunk was in the top 20 but not the top 5, and expect the filter to help most when many sibling documents are near-duplicates, which is true of this corpus by design. Neither can rescue a chunk that wasn't in the pool at all, so if a question still misses after both, go back and look at parsing and chunking. Rerank latency depends on your hardware; on a CPU it's typically the slowest step in the whole pipeline.

Project

Project · Chat with 100 messy PDFs

The labs ran on 12 manuals. This project scales the winning pipeline to 100, wraps it in a function a chat app can call, answers with citations that point at a specific page of the source PDF, caches repeat questions, and writes down what each upgrade was worth.

  1. Generate the bigger corpus and re-run your saved Lab 1 baseline (naive_rag_v1.py) on it first. The number you get here is the "before" in your results table.
    python rag/generate_corpus.py 100 python rag/naive_rag_v1.py
    Parsing the five scans costs a few vision-model calls per page, once; they are cached after that.
  2. Create rag/pipeline.py, the one function the app calls. It checks a semantic cache first (the same idea as Module 1, Lab 5: embed the question, return the stored answer if the nearest earlier question clears your threshold), otherwise runs hybrid retrieval, product filter and rerank, then asks the model for an answer that cites [doc p.N] tags. It reports latency and token counts for every call.
    import os, time import numpy as np from openai import OpenAI from common import embed from hybrid import chunks from rerank_filter import retrieve_rerank client = OpenAI(api_key=os.environ["OPENAI_API_KEY"]) CACHE_THRESHOLD = 0.95 # Re-tune this on YOUR questions. Two questions that differ only # in the product name score very high, and must NOT share an answer. _cache = [] # list of (question_vector, result_dict) def _cache_lookup(q_vec): for vec, result in _cache: sim = float(vec @ q_vec / (np.linalg.norm(vec) * np.linalg.norm(q_vec))) if sim >= CACHE_THRESHOLD: return result return None def ask(question): t0 = time.perf_counter() q_vec = embed([question])[0] hit = _cache_lookup(q_vec) if hit: return {**hit, "cached": True, "latency_ms": (time.perf_counter() - t0) * 1000, "input_tokens": 0, "output_tokens": 0} top = [chunks[i] for i in retrieve_rerank(question, 5, use_filter=True)] context = "\n\n".join(f"[{c['doc']} p.{c['page']}]\n{c['text']}" for c in top) resp = client.chat.completions.create( model="gpt-4.1-mini", max_tokens=300, messages=[{"role": "system", "content": "Answer using only the context. After each fact, cite its " "source tag exactly as written, like [doc.pdf p.2]. If the context does not contain " "the answer, say so and do not guess."}, {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {question}"}]) result = {"answer": resp.choices[0].message.content, "sources": [{"doc": c["doc"], "page": c["page"]} for c in top], "contexts": [c["text"] for c in top]} _cache.append((q_vec, result)) return {**result, "cached": False, "latency_ms": (time.perf_counter() - t0) * 1000, "input_tokens": resp.usage.prompt_tokens, "output_tokens": resp.usage.completion_tokens} if __name__ == "__main__": for q in ["How long is the warranty on the Larkfield Delta Sensor?", "How long is the warranty on the Larkfield Delta Sensor?", # repeat -> cache hit "How long is the warranty on the Larkfield Cobalt Pump?"]: # similar but different -> miss r = ask(q) print(f"cached={r['cached']!s:5} {r['latency_ms']:6.0f} ms in={r['input_tokens']} out={r['output_tokens']} {q}") print(" ", r["answer"][:120].replace("\n", " "))
    Use the cache threshold you found safe in Module 1, not a number copied from here. The cache must hold the sources alongside the answer, so a cache hit still shows citations.
  3. Build your "before and after" table. Re-run the recall measurement after each upgrade in this order, and add a row each time: naive baseline, layout parser plus OCR, structure-aware chunks, context prefix, hybrid search, rerank, filter. Save it as rag/results.md. The goal isn't a high final number; it's knowing which single change was worth the most, and which ones barely mattered.
  4. Put a thin app on top. Any web framework works. The one requirement that makes citations real: serve the PDFs, and make each citation a link of the form /corpus/<doc>#page=<N>, which browsers' built-in PDF viewers jump straight to.
