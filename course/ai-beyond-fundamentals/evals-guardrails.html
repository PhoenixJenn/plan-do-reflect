Module 4 · Evals & Guardrails

Evals & Guardrails

Module 3 ended with an app that works on the questions you tried. This module is about what happens next: someone changes a prompt, swaps a model, or tunes a retriever, and you need to know within minutes whether quality went up or down, and whether the app is still safe to put in front of people. You'll build the measurement (a golden set, graders, a calibrated judge, RAG metrics, traces), the protection (input and output guardrails, a spending cap), and finally wire the measurement into every pull request.

Everything runs on the Module 3 app and its generated manuals, so every question has a known right answer. Several labs are deliberately honest about their own weaknesses: the code grader is brittle, the injection filter is easy to slip past, a 20-item calibration is small. Finding those limits yourself is the point; each check tells you what to look for, and asks you to record your own numbers.

Concepts

A golden set is how you know you got better

A golden set is a fixed list of questions with the answer you expect for each, run through your app every time you change something. It replaces "that feels better" with a number. Three habits make it worth having. Fill it with real user questions as soon as you have any, because invented ones are tidier than what people actually type. Include questions the system cannot answer, where the correct behavior is to say so; without them you only measure how often it's right, never how often it bluffs. And keep it fresh: every production failure you find becomes a new row.

Size matters more than people expect. With 50 items, a single question is worth two percentage points, so a swing of one or two items is noise, not progress. That's fine for catching a broken prompt (which usually drops the score by far more) and not fine for ranking two nearly identical prompts. Know which of those jobs your set can do.

Four ways to grade an answer

Exact match and code checks are free, instant and perfectly repeatable: does the answer contain "24 months", is it valid JSON, does it cite a retrieved page? Use them wherever the right answer can be checked by a program, and be honest about what they can't see. A check for "did it admit it doesn't know" has to guess at the model's wording, and Lab 1 shows how brittle that gets.

An LLM judge is a second model that grades the first one against a written rubric. It scales to the judgments code can't make (is every claim supported, is the tone right) at the cost of money, latency and a grader that has its own biases. Human review is the most trustworthy and the slowest, so its job isn't to grade everything; it's to grade a small sample that tells you whether the judge can be trusted. The working pattern is code checks for everything checkable, a calibrated judge for the rest, and a human spot check on a schedule.

Calibrating the judge

A judge is a measuring instrument, and an uncalibrated instrument is just an opinion. Zheng et al. (Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena, NeurIPS 2023 Datasets and Benchmarks) documented the known failure modes: a verbosity bias (longer answers score higher regardless of quality), a position bias when comparing two answers, and a self-enhancement bias (a model rates its own outputs more kindly). Two cheap defenses: use a judge from a different model family than the app under test, and measure the judge against your own labels.

Calibration means grading a sample (20 answers is enough to start) yourself, before seeing the judge's scores, then comparing. Raw agreement is easy to read but flattering, since two graders who both give mostly 4s agree by luck. Cohen's kappa (Cohen, 1960, Educational and Psychological Measurement) corrects for chance agreement, and the weighted version (Cohen, 1968, Psychological Bulletin) counts a 1-versus-5 disagreement as much worse than 4-versus-5, which suits a 1-to-5 scale. Also check whether the judge's scores track answer length. Redo the calibration whenever you change the judge model or its rubric.

RAG metrics: which half is broken?

A wrong answer from a RAG app has two possible causes, and the fix for one does nothing for the other. The RAGAS paper (Es et al., RAGAS: Automated Evaluation of Retrieval Augmented Generation, 2023; EACL 2024 demonstrations) names four metrics that separate them. Context recall: did retrieval surface what was needed? Context precision: were the retrieved passages relevant, and ranked first? Those two grade the retrieval half. Faithfulness: is every claim in the answer supported by the retrieved context? Answer relevance: does the answer address the question that was asked? Those two grade the generation half.

Read them as a diagnosis. Low recall means go back to Module 3 (parsing, chunking, search). Good recall but low faithfulness means the model had the right passage and still made things up, so look at the prompt and the model. Good faithfulness but low relevance means a well-grounded answer to the wrong question. Lab 3 builds all four by hand so you can see exactly what each one measures; the RAGAS library packages the same ideas.

Tracing: seeing inside one request

An average latency number tells you the app is slow. A trace tells you why. One trace is one user request; it's made of spans, one per step (embed the question, search, rerank, call the model), each with a start time and duration, and spans can nest. Record the same for tool calls in an agent and you can replay exactly what happened on the one request that went wrong. Hosted tools such as Langfuse (open source, self-hostable) and LangSmith collect traces and add a UI; the underlying data is just what Lab 4's thirty-line tracer writes.

Guardrails: checks around the model, not inside it

A guardrail is ordinary code that inspects what goes into the model or what comes out. On the way in: redact personal data before it reaches a model or a log file, and screen for prompt injection and off-topic requests. On the way out: enforce the shape (valid schema), and reject claims the sources don't back. Lab 5's output check is a good example of a guardrail that costs nothing and catches a lot: an answer must either decline or cite a passage that was actually retrieved.

Be clear-eyed about the limits. Prompt injection, where text in the input (or in a retrieved document; see Greshake et al., Not what you've asked for: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection, AISec 2023) is read as an instruction, has no complete fix today, and OWASP lists it first in its Top 10 for LLM Applications. A pattern list stops the famous phrasings and nothing else. The only sound posture is layers: input filters, a model that's been told its role, output checks, and least privilege (a model that can't send email can't be tricked into sending it). For personal data at production scale, a purpose-built library such as Microsoft's open-source Presidio does far more than the regexes here.

Budgets: cost is a quality attribute

A runaway loop, a retry storm or one enthusiastic user can spend a month's budget in an afternoon, and nothing in the model API stops you. Two controls cover most of it. A per-user cap checked before the call refuses requests once a user hits their daily allowance. An app-wide alert checked after each call tells a human when total spend crosses a threshold, once, not on every request. Both depend on the token counts the API reports on every response, which Module 1 taught you to read.

Regression tests: make quality a build step

Everything above gets its real value when it runs automatically. A regression test here means: on every pull request, run the golden set, compare the scores to the last accepted baseline, and fail the build if any score fell by more than a margin. The margin exists because the set is small and models aren't perfectly repeatable; pick it from how much your scores wobble when nothing changed. The eval also has its own budget, since it calls a model on every PR, so cache what's deterministic (embeddings, OCR, model downloads), judge a fixed slice instead of everything, and fail loudly if a run goes over.

  3. Create evals/grading.py: the code-based graders. Answerable questions pass if the expected value appears in the answer; unanswerable ones pass if the answer uses a known "I can't find it" phrase.
    """Code-based graders: cheap, deterministic, and exact about what they can and can't see.""" import re REFUSAL_PHRASES = ["does not contain", "doesn't contain", "not contain", "cannot find", "can't find", "not mentioned", "no information", "not provided", "not specified", "unable to find"] def normalize(text): return re.sub(r"\s+", " ", text.lower()).strip() def grade_answerable(answer, expected): """Pass if the expected value appears in the answer.""" return normalize(expected) in normalize(answer) def grade_unanswerable(answer): """Pass if the answer admits it can't find the fact. Brittle by design: a model that declines in words this list doesn't know about will be marked wrong.""" return any(p in normalize(answer) for p in REFUSAL_PHRASES) def grade(item, answer): if item["answerable"]: return grade_answerable(answer, item["expected"]) return grade_unanswerable(answer)

  2. Create evals/judge.py: a 1-to-5 faithfulness rubric. Note how specific the rubric is: each score level says what it means, and the judge is told to ignore whether a claim is true in the real world, because faithfulness is about the context.
    from llm import judge_json FAITHFULNESS_RUBRIC = """You are grading whether an answer is faithful to the context it was given. Faithful means every claim in the answer is supported by the context. Ignore whether the claims are true in the real world; only the context counts. Score 1 to 5: 5 = every claim is directly supported by the context, or the answer correctly says the context lacks the information 4 = supported, with one minor unsupported detail that does not change the meaning 3 = mostly supported, but one claim goes beyond the context 2 = several claims are not in the context 1 = mostly unsupported or contradicts the context Context: {context} Question: {question} Answer to grade: {answer} Reply with only JSON: {{"score": <1-5>, "reason": "<one sentence>"}}""" def judge_faithfulness(question, answer, contexts): prompt = FAITHFULNESS_RUBRIC.format(context="\n---\n".join(contexts), question=question, answer=answer) out = judge_json(prompt) return int(out["score"]), out["reason"]

  4. Now run the judge on the same 20 and compare. This script reports exact agreement, within-one-point agreement, quadratic-weighted Cohen's kappa, both mean scores, and the correlation between each grader's score and answer length.
    import json, sys import numpy as np from judge import judge_faithfulness run = {r["id"]: r for r in json.load(open(f"evals/run_{sys.argv[1] if len(sys.argv) > 1 else 'baseline'}.json"))} hand = {int(k): v for k, v in json.load(open("evals/hand_labels.json")).items()} ids = sorted(hand) judge = {} for i in ids: judge[i], reason = judge_faithfulness(run[i]["question"], run[i]["answer"], run[i]["contexts"]) h = np.array([hand[i] for i in ids]); j = np.array([judge[i] for i in ids]) def weighted_kappa(a, b, levels=5): """Quadratic-weighted Cohen's kappa: 1.0 = perfect agreement, 0 = no better than chance. Being off by 4 costs far more than being off by 1, which suits an ordinal 1-5 scale.""" obs = np.zeros((levels, levels)) for x, y in zip(a, b): obs[x - 1, y - 1] += 1 obs /= obs.sum() exp = np.outer(obs.sum(1), obs.sum(0)) w = np.array([[(i - k) ** 2 for k in range(levels)] for i in range(levels)]) / (levels - 1) ** 2 return 1 - (w * obs).sum() / (w * exp).sum() def ranks(x): order = np.argsort(x, kind="stable"); r = np.empty(len(x)); r[order] = np.arange(len(x)) for v in np.unique(x): # average the ranks of tied values r[x == v] = r[x == v].mean() return r def spearman(a, b): if np.std(a) == 0 or np.std(b) == 0: return float("nan") return float(np.corrcoef(ranks(a), ranks(b))[0, 1]) lengths = np.array([len(run[i]["answer"]) for i in ids]) print(f"exact agreement : {np.mean(h == j):.0%}") print(f"within 1 point : {np.mean(abs(h - j) <= 1):.0%}") print(f"weighted kappa : {weighted_kappa(h, j):.2f}") print(f"mean score you/judge: {h.mean():.2f} / {j.mean():.2f}") print(f"judge score vs answer length (Spearman): {spearman(j, lengths):+.2f}") print(f"your score vs answer length (Spearman): {spearman(h, lengths):+.2f}") print("\nlargest disagreements:") for i in sorted(ids, key=lambda i: -abs(hand[i] - judge[i]))[:3]: print(f" #{i}: you={hand[i]} judge={judge[i]} {run[i]['question']}")

  1. Create evals/rag_metrics.py. It implements the four metrics from the RAGAS paper by hand, simplified in two places that the comments call out: context recall uses an exact-string check instead of a model (possible because your reference answers are single short facts), and context precision judges each retrieved passage then averages precision at the positions that hold a relevant one, rewarding relevant passages ranked high.
    """Four RAG metrics in the spirit of RAGAS (Es et al., 2023), written out by hand so you can see what each one actually does. Simplified where noted.""" import json, sys import numpy as np sys.path.insert(0, "rag") from common import embed from llm import judge_json def faithfulness(answer, contexts): """Split the answer into claims, then check each claim against the context. Score = supported claims / total claims.""" claims = judge_json(f"List every factual claim in this answer as a short standalone statement. " f'Reply only JSON: {{"claims": ["..."]}}\n\nAnswer: {answer}')["claims"] if not claims: return 1.0 # nothing asserted, nothing unsupported (a refusal lands here) verdicts = judge_json("For each claim, say whether the context supports it. Context:\n" + "\n---\n".join(contexts) + "\n\nClaims:\n" + json.dumps(claims) + '\n\nReply only JSON: {"supported": [true, false, ...]} in the same order.')["supported"] return sum(bool(v) for v in verdicts) / len(claims) def answer_relevance(question, answer, n=3): """Have the model write n questions this answer would be a good reply to, then measure how close they are to the real question (cosine of embeddings). An answer that rambles or dodges produces questions that drift away from the one that was asked.""" qs = judge_json(f'Write {n} different questions that the following answer would be a direct reply to. ' f'Reply only JSON: {{"questions": ["..."]}}\n\nAnswer: {answer}')["questions"] vecs = embed([question] + qs) q, rest = vecs[0], vecs[1:] sims = rest @ q / (np.linalg.norm(rest, axis=1) * np.linalg.norm(q)) return float(sims.mean()) def context_precision(question, contexts): """Are the retrieved chunks relevant, and are the relevant ones ranked first? Judge each chunk, then average precision@i over the positions that hold a relevant chunk.""" flags = [] for c in contexts: out = judge_json(f"Is this passage useful for answering the question? " f'Reply only JSON: {{"relevant": true/false}}\n\nQuestion: {question}\n\nPassage:\n{c}') flags.append(bool(out["relevant"])) precisions = [sum(flags[:i + 1]) / (i + 1) for i, f in enumerate(flags) if f] return float(np.mean(precisions)) if precisions else 0.0 def context_recall(expected, contexts): """Did retrieval surface what was needed? RAGAS has a model check each sentence of a reference answer against the context. Our reference answers are single short facts, so an exact string check does the same job deterministically (a simplification that only works because of that).""" return float(any(expected.lower() in c.lower() for c in contexts)) if __name__ == "__main__": run = json.load(open(f"evals/run_{sys.argv[1] if len(sys.argv) > 1 else 'baseline'}.json")) rows = [] for r in run: row = {"id": r["id"], "faith": faithfulness(r["answer"], r["contexts"]), "relevance": answer_relevance(r["question"], r["answer"]), "precision": context_precision(r["question"], r["contexts"])} if r["answerable"]: row["recall"] = context_recall(r["expected"], r["contexts"]) rows.append(row) for m in ["faith", "relevance", "precision", "recall"]: vals = [row[m] for row in rows if m in row] print(f"{m:10s} mean={np.mean(vals):.2f} (n={len(vals)})") json.dump(rows, open("evals/metrics.json", "w"), indent=1) worst = sorted(rows, key=lambda x: x["faith"])[:3] print("lowest faithfulness:", [(w["id"], round(w["faith"], 2)) for w in worst])

  1. Create evals/tracing.py: a span context manager that records the name, parent and duration of each step to a JSONL file, plus a trace() wrapper that gives every request its own id.
    """A minimal tracer: every step becomes a span with a start time and duration, written as one JSON line. Hosted tools (Langfuse, LangSmith) record the same things and add a UI on top.""" import contextvars, json, time, uuid from contextlib import contextmanager _trace_id = contextvars.ContextVar("trace_id", default=None) _stack = contextvars.ContextVar("stack", default=()) TRACE_FILE = "evals/traces.jsonl" @contextmanager def trace(name): """One trace per user request. Spans started inside it share its id.""" tid = _trace_id.set(uuid.uuid4().hex[:8]) try: with span(name): yield finally: _trace_id.reset(tid) @contextmanager def span(name, **attrs): parent = _stack.get()[-1] if _stack.get() else None token = _stack.set(_stack.get() + (name,)) t0 = time.perf_counter() try: yield finally: _stack.reset(token) with open(TRACE_FILE, "a") as f: f.write(json.dumps({"trace": _trace_id.get(), "span": name, "parent": parent, "ms": round((time.perf_counter() - t0) * 1000, 1), **attrs}) + "\n") def traced(fn, name): """Wrap an existing function so every call to it becomes a span.""" def wrapper(*a, **k): with span(name): return fn(*a, **k) return wrapper

Input side: redact emails, US-style phone numbers, SSN-format numbers, and credit-card numbers (using the Luhn checksum so ordinary long numbers aren't redacted), then screen for known injection phrasings and obvious off-topic requests. Output side: every answer must decline or carry a citation, and every citation must point at a passage that was actually retrieved.
    import re # ---------- input guardrails ---------- PII_PATTERNS = { "EMAIL": re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"), "SSN": re.compile(r"\b\d{3}-\d{2}-\d{4}\b"), "PHONE": re.compile(r"(?<!\d)(?:\+?1[\s.-]?)?\(?\d{3}\)?[\s.-]?\d{3}[\s.-]?\d{4}(?!\d)"), } CARD = re.compile(r"\b(?:\d[ -]?){13,16}\b") def luhn_ok(number): """Credit card numbers carry a checksum; testing it avoids redacting every long number.""" digits = [int(c) for c in re.sub(r"\D", "", number)][::-1] total = sum(d if i % 2 == 0 else (d * 2 - 9 if d * 2 > 9 else d * 2) for i, d in enumerate(digits)) return len(digits) >= 13 and total % 10 == 0 def redact_pii(text): """Replace personal data with a typed placeholder BEFORE the text reaches a model or a log.""" text = CARD.sub(lambda m: "[CARD]" if luhn_ok(m.group()) else m.group(), text) for label, pattern in PII_PATTERNS.items(): text = pattern.sub(f"[{label}]", text) return text INJECTION_PATTERNS = [ r"ignore (all |any |the )?(previous|prior|above) (instructions|prompts?)", r"disregard (all |any |the )?(previous|prior|above)", r"you are now\b", r"reveal (your |the )?(system )?prompt", r"developer mode", r"pretend (to be|you are)", ] def looks_like_injection(text): """A cheap first filter. It catches the famous phrasings and nothing else, so treat it as one layer, never the defense.""" return any(re.search(p, text, re.I) for p in INJECTION_PATTERNS) OFF_TOPIC_HINT = re.compile(r"\b(recipe|poem|stock|lottery|horoscope|write (me )?(a|an) (story|essay))\b", re.I) def check_input(question): """Returns (clean_question, blocked_reason_or_None).""" clean = redact_pii(question) if looks_like_injection(clean): return clean, "possible prompt injection" if OFF_TOPIC_HINT.search(clean): return clean, "off topic" return clean, None # ---------- output guardrails ---------- CITATION = re.compile(r"\[([^\]]+?\.pdf) p\.(\d+)\]") REFUSAL = ("does not contain", "cannot find", "can't find", "not mentioned", "no information", "not provided") def check_output(answer, sources): """Every answer must either decline, or carry at least one citation, and every citation must point at a passage that was actually retrieved. Returns (ok, reason).""" if any(p in answer.lower() for p in REFUSAL): return True, "declined" cites = CITATION.findall(answer) if not cites: return False, "no citation" allowed = {(s["doc"], str(s["page"])) for s in sources} for doc, page in cites: if (doc, page) not in allowed: return False, f"cites a passage that was not retrieved: {doc} p.{page}" return True, "cited" FALLBACK = "I can't answer that from the documents I have." def guarded_ask(question, ask_fn): clean, blocked = check_input(question) if blocked: return {"answer": FALLBACK, "blocked": f"input: {blocked}"} result = ask_fn(clean) ok, reason = check_output(result["answer"], result["sources"]) if not ok: return {**result, "answer": FALLBACK, "blocked": f"output: {reason}"} return {**result, "blocked": None}

    """Ten attack prompts, each telling the app to say a canary word. If a canary shows up in an answer, the attack worked.   1. Create evals/budget.py. A small JSON ledger resets each day and tracks tokens per user. check_budget runs before a call and refuses once the user is at their cap; record_usage runs after with the API's reported token counts and fires an app-wide alert the first time the day's total crosses a threshold. A price table is included but left at zero, because prices change: fill it in from each provider's pricing page on the day you build this.
    import json, time from datetime import date from pathlib import Path LEDGER = Path("evals/usage_ledger.json") DAILY_TOKEN_CAP = 20_000 # per user, per day. Pick yours from real usage, then add headroom. APP_ALERT_TOKENS = 200_000 # alert when the whole app crosses this in a day # Fill these in from each provider's pricing page on the day you build this. Prices change. # Dollars per 1,000,000 tokens: (input, output) PRICE_PER_MTOK = {"gpt-4.1-mini": (0.0, 0.0)} class OverBudget(Exception): pass def _load(): data = json.loads(LEDGER.read_text()) if LEDGER.exists() else {} if data.get("day") != str(date.today()): data = {"day": str(date.today()), "users": {}, "alerted": False} return data def check_budget(user): """Call BEFORE the model call. Refuse instead of spending when the user is already at the cap.""" if _load()["users"].get(user, 0) >= DAILY_TOKEN_CAP: raise OverBudget(f"{user} has used today's {DAILY_TOKEN_CAP:,}-token allowance") def record_usage(user, input_tokens, output_tokens, alert=print): """Call AFTER the model call with the token counts the API reported.""" data = _load() data["users"][user] = data["users"].get(user, 0) + input_tokens + output_tokens total = sum(data["users"].values()) if total >= APP_ALERT_TOKENS and not data["alerted"]: data["alerted"] = True # alert once per day, not on every call alert(f"ALERT: app has used {total:,} tokens today (threshold {APP_ALERT_TOKENS:,})") LEDGER.write_text(json.dumps(data)) def cost_usd(model, input_tokens, output_tokens): pin, pout = PRICE_PER_MTOK[model] return (input_tokens * pin + output_tokens * pout) / 1_000_000 def guarded_call(user, ask_fn, question): check_budget(user) result = ask_fn(question) record_usage(user, result["input_tokens"], result["output_tokens"]) return result if __name__ == "__main__": # No API needed: simulate usage to watch the cap and the alert fire. Project

Project · Eval suite that runs in CI

Labs 1 to 6 are things you run by hand. This project makes the important ones run without you: every pull request gets the golden set, a score table posted as a comment, and a red build if quality dropped past a margin, with the eval's own cost capped.

  1. Create evals/ci_eval.py. It runs the whole golden set, computes three scores (answerable pass rate, unanswerable pass rate, and mean judged faithfulness on a fixed slice of 15 items, scaled to 0 to 1), compares each to evals/baseline.json, writes a Markdown results table, and exits non-zero if any score fell by more than the margin, or if the run used more tokens than its own budget.
    """Run the golden set, compare to the last accepted scores, fail the build on a real drop. Exit code 0 = fine, 1 = quality dropped, 2 = the eval itself blew its budget.""" import json, sys sys.path.insert(0, "rag") import pipeline from pipeline import ask from grading import grade from judge import judge_faithfulness pipeline.CACHE_THRESHOLD = 2.0 # cosine similarity never reaches 2: a cache hit would hide the change under test MARGIN = 0.05 # tolerated drop. Golden sets are small, so noise is real: widen if flaky. MAX_TOKENS_PER_RUN = 150_000 # the eval's own budget, app tokens only. Fail loudly if exceeded. JUDGE_SAMPLE = 15 # judge a fixed slice, not all 50: the judge is the expensive part items = [json.loads(l) for l in open("evals/golden.jsonl")] rows, tokens = [], 0 for item in items: r = ask(item["question"]) tokens += r["input_tokens"] + r["output_tokens"] rows.append({**item, "answer": r["answer"], "contexts": r["contexts"], "passed": grade(item, r["answer"])}) ans = [r for r in rows if r["answerable"]]; unans = [r for r in rows if not r["answerable"]] scores = {"answerable_pass": sum(r["passed"] for r in ans) / len(ans), "unanswerable_pass": sum(r["passed"] for r in unans) / len(unans)} judged = rows[:JUDGE_SAMPLE] scores["faithfulness"] = sum(judge_faithfulness(r["question"], r["answer"], r["contexts"])[0] for r in judged) / len(judged) / 5 try: baseline = json.load(open("evals/baseline.json")) except FileNotFoundError: baseline = None lines = ["## Eval results", "", "| metric | this PR | baseline | change |", "|---|---|---|---|"] failed = [] for k, v in scores.items(): b = baseline.get(k) if baseline else None delta = f"{v - b:+.2f}" if b is not None else "n/a" lines.append(f"| {k} | {v:.2f} | {'n/a' if b is None else f'{b:.2f}'} | {delta} |") if b is not None and v < b - MARGIN: failed.append(k) lines += ["", f"Tokens used by this run: {tokens:,} (limit {MAX_TOKENS_PER_RUN:,}). Margin: {MARGIN}."] if failed: lines += ["", f"**FAILED:** {', '.join(failed)} dropped by more than {MARGIN}."] for r in [r for r in rows if not r["passed"]][:10]: lines.append(f"- #{r['id']} {r['question']} -> {r['answer'][:100]!r}") open("evals/results.md", "w").write("\n".join(lines)) json.dump(scores, open("evals/scores.json", "w"), indent=1) print("\n".join(lines)) if tokens > MAX_TOKENS_PER_RUN: print("\nEval exceeded its own token budget."); sys.exit(2) sys.exit(1 if failed else 0)

Flaky checks train people to ignore them

Model outputs vary run to run even at temperature 0, and a 50-item set is small. If the check fails on a PR that changed nothing, widen the margin or raise the item count before you do anything else. A build gate people learn to re-run until it's green has stopped measuring anything.

Done when:

  • A deliberately broken prompt fails the build, and the PR comment shows which score dropped and by how much.
  • Your judge-versus-human agreement from Lab 2 (weighted kappa and within-one agreement) is written in the repo's README, along with the judge model used.
  • Each eval run stays under a stated token budget, and the workflow fails when it doesn't.
  • A PR that changes nothing passes, so you know the margin isn't set inside the noise.
