LLM Fundamentals

Module 0 gave you shared/llm_client.py — one function that calls any provider and logs what it cost. This module is about understanding what's actually happening inside that call well enough to predict the cost and the latency before you make it, not just read them off afterward: what a token is, what temperature and streaming actually change, and the two completely different kinds of caching that cut cost without you noticing.

Concepts

Messages, roles, and system prompts — and why the shapes differ

Every provider's chat API takes a list of turns, each tagged with a role: user for what you send, assistant for what the model said, and a system prompt that sets standing behavior ("answer only from the provided text," "respond in JSON") before the conversation starts.

Where that system prompt goes is the one thing that genuinely differs per provider, and it's exactly the kind of difference a shared client has to hide. (Module 0's call() sends no system prompt yet, only the user's message; the chat client you build in this module's project adds one.) Anthropic takes system as its own top-level parameter, separate from messages. OpenAI (and Ollama, through the same OpenAI-compatible SDK) treats it as just another message with role: "system". Gemini takes a top-level systemInstruction (like Anthropic's system, not a message), and its own role for the model's turns is "model", not "assistant", which trips people up the first time they build multi-turn history by hand.

The table below puts the shapes side by side. Each link goes to that provider's own API reference, where you can see the complete request payload with every optional field.

Tokens, context windows, and cost

A token is the unit a model actually reads and writes — usually a few characters or a word-piece, not a whole word. Different providers use different tokenizers, so the same sentence costs a different number of tokens depending on who's counting; Lab 1 makes that concrete instead of abstract.

The context window is the most tokens a single call can hold — input and output combined, for most providers. Go over it and the call fails outright; it doesn't quietly truncate for you. Cost is just arithmetic on top of the token count, and it's the exact formula already sitting in Module 0's call(): input_tokens / 1_000_000 * price_in + output_tokens / 1_000_000 * price_out. Output tokens are usually the expensive half of that sum — providers price them several times higher than input, because generating a token costs more compute than reading one.

Sampling settings: temperature, top-p, max tokens, stop sequences

Temperature controls how much the model is allowed to deviate from its single most-likely next token — near 0 it's close to deterministic, higher values let lower-probability tokens win sometimes. top-p is a second, related knob (nucleus sampling: only consider tokens whose combined probability covers the top p) — most people pick one of the two to tune and leave the other at its default rather than fighting both at once.

What range is allowed depends on the provider, and on the model. We tested the models this course uses:

Provider and modelTemperature
OpenAI gpt-5.4-mini0 to 2. A value above 2 returns a 400 error.
Gemini gemini-flash-lite-latest0 to 2. A value above 2 returns a 400 error.
Ollama (local model)Accepted every value we tried, up to 5, with no error. Don't read that as meaningful: very high values just produce noise.
Anthropic claude-haiku-5-5Not accepted at all. The API returns a 400 (temperature: Extra inputs are not permitted), and so do top_p and top_k. Earlier Claude models accepted 0 to 1, so check the docs for the model you use.

That is why Lab 3 sweeps temperature on OpenAI and not on Claude. It is also a reason to read a model's API reference before copying settings from an older tutorial.

max_tokens is a hard ceiling on the reply's length, not a target — the model can stop earlier on its own, but never later. It doesn't affect input cost at all, only caps how much output you could be charged for. Stop sequences end generation early the instant a given string appears, useful for formats where you know the reply should end at a specific marker.

Streaming: time to first token vs. total latency

A blocking call waits for the entire reply before returning anything. A streaming call returns the first chunk as soon as the model has generated it, then keeps delivering chunks as they're produced. Time to first token (TTFT) is how long the first chunk takes; total latency is how long the whole reply takes either way. Streaming barely changes total latency — the model still has to generate every token — but it changes what the user experiences: they see something moving almost immediately instead of staring at a blank screen for the full duration.

The object you iterate to get those chunks is different per SDK: Anthropic gives you a context manager with a .text_stream you loop over; OpenAI (and Ollama) give you an iterator of chunk objects where the text lives at chunk.choices[0].delta.content; Gemini gives you an iterator where it's just chunk.text.

Caching: two different mechanisms, easy to conflate

Prompt caching is the provider reusing its own internal computation (the "KV cache") for a prefix of tokens it has already processed, so a second call that repeats the same long system prompt or document doesn't re-pay for reprocessing it. It requires an identical prefix — one character different and it's a cache miss. Anthropic requires you to mark the cacheable block explicitly with cache_control; OpenAI does it automatically for any prompt over roughly 1,024 tokens, no code change required.

Semantic caching is a completely different, application-level idea: you embed the question itself and compare it by similarity to questions you've answered before, returning the stored answer if it's close enough — even if the wording doesn't match at all. It catches paraphrases that prompt caching can't touch, because prompt caching never looks at whether two questions mean the same thing, only whether the bytes match.

Picking a model: quality, speed, cost — pick two

There's no universally "best" model, only a triangle you're trading off inside: bigger and smarter models cost more and respond slower; smaller "lite" or "mini" variants are cheaper and faster but weaker on hard tasks. The practical move (and the subject of Module 6's router lab) is routing easy requests to a cheap model and reserving the expensive one for requests that actually need it.

That tradeoff isn't hypothetical here: both Module 0 and this module use gemini-flash-lite-latest rather than gemini-flash-latest, specifically because the lite variant answered reliably and fast under real testing (under a second for a short reply), while the larger flash models were overloaded and timed out with 503 and 504 errors. Cheaper and faster isn't always a downgrade — sometimes it's just the better fit for what you're doing.

A chat API has no memory. Every turn, your code sends the entire conversation again: the system prompt, every earlier question, and every earlier answer. This lab makes that visible and shows why clear, compact prompts are a cost and quality skill, not just a style preference.

Why clear and compact matters

Wordy prompts cost you three times: they are billed when you send them, they are billed again on every later turn, and they invite long answers that are also billed again on every later turn. Long conversations also push toward the context window limit, where the call fails. The fixes are the skills this course keeps coming back to: say what you want in fewer words, ask for short answers when short is enough, and start a fresh conversation (or summarize the old one) instead of dragging a long history along.

  1. Create chatbot/temperature_sweep.py and paste in a function that calls the same prompt n times at a given temperature and collects the answers.
    import os from dotenv import load_dotenv load_dotenv() from openai import OpenAI client = OpenAI(api_key=os.environ["OPENAI_API_KEY"]) PROMPT = "Name an animal. Reply with just the word." def sweep(temperature, n=10): answers = [] for _ in range(n): resp = client.chat.completions.create( model="gpt-5.4-mini", max_completion_tokens=15, temperature=temperature, messages=[{"role": "user", "content": PROMPT}], ) answers.append(resp.choices[0].message.content.strip().lower()) # lower() so "Elephant" and "elephant" count as one answer return answers if __name__ == "__main__": for temp in [0, 1, 1.8]: answers = sweep(temp) print(f"temp={temp}: {answers} -> {len(set(answers))} distinct")
  2. Run it. Prompt choice matters here more than you'd expect: a narrowly-biased prompt like "name one primary color" stays stuck on whichever answer the model considers overwhelmingly likely (almost always "Red") even at the highest temperature, across all 10 tries — that's a real result if it happens to you, not a bug, it just doesn't make for an interesting lab. "Name an animal" has enough plausible alternatives that temperature actually has room to work.
    python chatbot/temperature_sweep.py
Check: distinct-answer count should rise with temperature, not stay flat. In our own run: temp=0 → 1 distinct (10/10 "elephant"); temp=1 → 3 distinct (seven "elephant", two "dolphin", one "octopus"); temp=1.8 → 5 distinct ("elephant", "dolphin", "otter", "aardvark", "octopus"). Newer OpenAI models reject max_tokens and want max_completion_tokens instead, which is why the call above uses that name. Don't expect temp=0 to be perfectly identical every single run forever; providers don't guarantee strict determinism even at 0. Sampling is random, so your counts will differ from ours, especially at temp=1, where ten samples can easily come back as 1, 2 or 3 distinct answers. The trend across the three temperatures is what matters; raise n to 30 if you want a clearer picture.

Notice "elephant" and "dolphin" still lead even at temp=1.8 — that's not noise, it's the real signal. The model's underlying probability distribution for "name an animal" isn't flat across every species; a handful of prototypical answers that show up constantly in training data (elephant, dolphin, lion, tiger) carry most of the probability mass, with thousands of other real animals each holding a tiny sliver of the rest. Temperature rescales that distribution so lower-probability tokens can win sometimes — which is why you see 4 distinct answers instead of 1 — but it doesn't flatten the distribution to uniform. If the two biggest peaks still hold most of the mass after rescaling, they'll still win most draws. "Higher temperature" means "more exposure to how peaked the real distribution already is," not "more randomness" in any general sense.

  1. Create chatbot/semantic_cache.py. It embeds a small seed set of question/answer pairs, then for any new question finds the closest seed by cosine similarity (plain Python — no numpy needed for three vectors) and returns its answer if the similarity clears a threshold.
    import os, math from dotenv import load_dotenv load_dotenv() from openai import OpenAI client = OpenAI(api_key=os.environ["OPENAI_API_KEY"]) def embed(texts): resp = client.embeddings.create(model="text-embedding-3-small", input=texts) return [d.embedding for d in resp.data] def cosine_similarity(a, b): dot = sum(x * y for x, y in zip(a, b)) na = math.sqrt(sum(x * x for x in a)) nb = math.sqrt(sum(x * x for x in b)) return dot / (na * nb) SEED = { "What is the capital of France?": "Paris.", "How many legs does a spider have?": "Eight.", "What's the boiling point of water in Celsius?": "100 degrees.", } seed_questions = list(SEED.keys()) seed_vecs = embed(seed_questions) def lookup(question, threshold): q_vec = embed([question])[0] best_score, best_q = 0, None for sq, sv in zip(seed_questions, seed_vecs): score = cosine_similarity(q_vec, sv) if score > best_score: best_score, best_q = score, sq if best_score >= threshold: return SEED[best_q], best_score, best_q return None, best_score, best_q
  2. Add a test set deliberately mixing three kinds of question — true paraphrases of a seed, questions on the same topic as a seed but asking something different, and fully unrelated questions — then sweep a few thresholds and print every score.
    TEST_QUESTIONS = [ # paraphrases -- should hit "Which city is the capital of France?", "What's France's capital city?", "How many legs do spiders have?", "What temperature does water boil at, in Celsius?", # same topic, different question -- should NOT hit "What is the population of France?", "How many eyes does a spider have?", "What's the freezing point of water in Celsius?", # unrelated -- should NOT hit "How do I bake a chocolate cake?", "What's the capital of Japan?", ] if __name__ == "__main__": for threshold in [0.95, 0.85, 0.75, 0.6]: print(f"--- threshold={threshold} ---") hits = 0 for q in TEST_QUESTIONS: answer, score, matched = lookup(q, threshold) status = f"HIT (matched {matched!r})" if answer else "miss" print(f" {score:.3f} {q!r} -> {status}") if answer: hits += 1 print(f" {hits}/{len(TEST_QUESTIONS)} hits\n")

Project · Chatbot with a live cost meter

Module 0's call(prompt, model) only handles one-shot, non-streaming calls — a chat app needs two things it doesn't have: a full conversation history instead of a single prompt, and streaming instead of waiting for the whole reply. Part 1 builds that as a terminal app. Part 2 is the same logic behind a minimal local web page, which is also where the one genuinely tricky bit of this project lives.

Part 1 · Terminal REPL

  1. Extend shared/llm_client.py with a streaming, multi-turn sibling to call(). It takes a full [{"role", "content"}, ...] history instead of one prompt string, and an on_chunk callback it calls once per piece of text as it streams — so a caller can print each piece the moment it arrives instead of waiting for the full reply.
    # shared/llm_client.py -- add below the existing call()/_dispatch() def stream_chat(messages, model, on_chunk=None, system=None, max_attempts=5): cfg = CONFIG[model] start = time.time() for attempt in range(max_attempts): try: text, usage = _dispatch_stream(cfg["provider"], model, messages, on_chunk, system) break except RATE_LIMIT_ERRORS: if attempt == max_attempts - 1: raise time.sleep(2 ** attempt + random.random()) elapsed_ms = (time.time() - start) * 1000 cost = (usage["input_tokens"] / 1_000_000 * cfg["price_in"] + usage["output_tokens"] / 1_000_000 * cfg["price_out"]) log_call(cfg["provider"], model, usage["input_tokens"], usage["output_tokens"], elapsed_ms, cost) return text, cost, elapsed_ms

Part 2 (Advanced) · Minimal local web app

Same chat, same stream_chat, running behind a one-page local Flask app instead of a terminal. The interesting problem here isn't the UI — it's that on_chunk is a plain callback with no way to pause itself and hand control back to Flask, which is exactly what an HTTP response generator needs to do between chunks.

  1. Install Flask.
    pip install flask pip freeze > requirements.txt
  2. Create chatbot/chat_web.py. The fix for the callback problem: run stream_chat on a background thread that pushes each chunk onto a queue.Queue, and let Flask's response generator just drain that queue — q.get() blocks until a chunk shows up, which is what turns "a callback fired" into "the generator can yield now."
    # chatbot/chat_web.py import sys, json, queue, pathlib, threading sys.path.insert(0, str(pathlib.Path(__file__).resolve().parent.parent / "shared")) from llm_client import stream_chat, CONFIG from flask import Flask, request, Response app = Flask(__name__) DONE_MARKER = "\x00DONE\x00" ERROR_MARKER = "\x00ERROR\x00" @app.route("/models") def models(): return {"models": list(CONFIG.keys())} @app.route("/chat", methods=["POST"]) def chat(): body = request.get_json() messages, model = body["messages"], body["model"] q = queue.Queue() def worker(): try: def on_chunk(c): q.put(("chunk", c)) text, cost, elapsed_ms = stream_chat(messages, model, on_chunk=on_chunk) q.put(("done", {"cost": cost, "elapsed_ms": elapsed_ms})) except Exception as e: q.put(("error", str(e))) threading.Thread(target=worker, daemon=True).start() def generate(): while True: kind, payload = q.get() if kind == "chunk": yield payload elif kind == "done": yield DONE_MARKER + json.dumps(payload) return elif kind == "error": yield ERROR_MARKER + payload return return Response(generate(), mimetype="text/plain")
  3. Add the / route and the page itself — a model <select>, a log, an input box, and JS that reads the streamed response body chunk by chunk, splitting out the DONE_MARKER footer to update the cost meter. The marker is a null byte sequence that will never appear in normal model output, so a plain string search finds it reliably.
    # add above the two routes in chat_web.py INDEX_HTML = """<!doctype html> <title>Cost-Meter Chat</title> <select id="model"></select> <div id="log" style="white-space:pre-wrap;border:1px solid #ccc;height:320px;overflow-y:auto;padding:10px"></div> <input id="input"><button id="send">Send</button> <div id="meter"></div> <script> let messages = [], sessionCost = 0;
