Module 7 · Ship It

Ship It

Everything so far ran for you, on your machine, on data you generated. This module puts one real thing in front of real people: a problem someone actually has, built with the pieces from Modules 1 to 6, deployed, measured where it runs, and written up honestly, including what broke. The through-line is that every claim you make about the project should be one a tool made and a check can verify.

This is the most open-ended module, so the lesson gives you structure and checks rather than a fixed task. The code here (a small web service, its tests, a secrets scanner, a production-metrics report, README and demo-script checkers, and a stranger test) was run and tested; none of it was deployed to a real host, so your cold-start, memory, latency and cost numbers are yours to measure. Each lab says exactly what was and wasn't verified.

Concepts

Shipping is part of the skill

A project that only runs on your laptop proves you can follow a tutorial. A project a stranger can open, run, and check proves a harder set of things: that you can scope a problem, make it reproducible, keep secrets secret, measure what it does in the real world, and be honest about where it fails. Those are the skills the earlier modules built toward, and this module is where they become visible to anyone but you.

The module's requirements say it plainly: a real problem, your own loop before a framework, both a RAG app and an agent deployed, a README whose numbers are measured, a 60-second demo, and a write-up of what broke. Each of those has a mechanical check in this lesson, because "I think the README is accurate" is exactly the kind of claim this course has trained you to distrust.

A real problem, and what "real" means

A tutorial problem is one nobody has. A real problem has a named person who has it now and would notice if it went away. The test is to ask that person about the last time it happened (what they did, how long it took, what it cost them) rather than whether they'd like your idea. Rob Fitzpatrick's The Mom Test (2013) is built around exactly this: people will politely endorse any idea, but they can't fake a specific recent memory.

Write the pitch before any code, with six fields: the user, the problem, why an LLM helps, how it could be done without an LLM, a success number, and what you are not building. The no-LLM field is Module 6 applied: if you can't explain why a lookup table or a rule isn't enough, you may not need the model. The not-building field is what keeps a six-week project from becoming a six-month one.

README first: the spec you can't skip

Writing the README before the code forces the decisions that bite later: who this is for, what the architecture is, what success looks like, and how a stranger will run it. A README written last records whatever you happened to build; one written first is the spec, and the code is checked against it.

The most important rule is about the numbers. A results table typed by hand drifts from reality the first time you change a prompt. So this lesson's pattern is that tools write the numbers: the eval suite writes its scores to a file, the production log produces latency and cost, a script fills the README table with each value's source file and date, and a check in CI fails if the table is stale, edited by hand, or contains a metric nobody measured. The rule "every number is measured, not estimated" becomes something a build can enforce.

What "deployed" requires

Hosting a script is the easy part. A service other people can hit needs a handful of properties, each of which prevents a specific bad day. Configuration from the environment: keys and limits are read from environment variables, never from files in the repo (the twelve-factor app's rule on config, from Adam Wiggins's 2011 The Twelve-Factor App), and a missing key stops the process at boot so you find out at deploy time, not at 2 a.m. A health check and a readiness check: the host asks "is the process alive?" and your app can answer "yes, but still loading the index", so traffic arrives only when you can serve it. Rate limiting, because an open endpoint that calls a paid model is an invitation to a surprise bill. Input limits on size and shape. And clean failures: a model outage returns a short error, never a stack trace.

Lab 3 builds all of these into one small service in front of your RAG app and your agent, with tests. Two honest caveats ride along. An in-memory rate limiter is per process, so a service with several instances needs a shared store. And the agent endpoint here runs the whole job before it answers, which is fine for a demo and wrong for real traffic, where you start a background job and let the client poll.

Measure it where it runs

Numbers measured on your laptop describe your laptop. In production you need three: latency (report the median and the 95th percentile, because users feel the slow tail), cost per request (from the token counts the API already returns, and with cache hits counted separately, since a hit costs nothing), and the error rate. The service in Lab 3 writes one structured log line per request, with the token counts and a hash of the question instead of the question itself, and a small script turns those lines into the numbers.

Two traps. Cold starts: some hosting tiers stop idle services, so the first request after a pause waits for the process to start and your index to load. Measure cold and warm separately and say which your README quotes. And memory: the reranker from Module 3 is a neural model, and hosts limit memory by plan. Check what your service uses idle and under load before you pick a plan; if it won't fit, replace the reranker or call a hosted one, and re-run your evals to see what that costs in quality.

Before it is public

Four checks, all cheap now and expensive later. Secrets: scan every tracked file for key-shaped strings before every push. A key that reaches a public repo should be treated as leaked, even if you delete the commit, because history and mirrors keep it; rotate it. Logs: don't log user text you don't need, and redact what you do (Module 4's redaction applies here). Exposure: the deployed agent should have only read-only tools, since a public endpoint can't pop up an approval prompt the way your terminal did in Module 5; anything that acts needs an explicit approval flow or must be left out. Licenses: check every dependency before you publish. Module 2 flagged that pymupdf4llm is licensed AGPL-3.0 (or commercially from Artifex), and AGPL has a network clause, so putting it behind a public service generally means publishing your source under AGPL or buying a commercial license. That's not legal advice, only a reason to look before you launch.

Product judgment: autonomy, trust and recoverability

Everything above is a skill you can get right by following a checklist. This is judgment, and it's the harder half: how much should the system be allowed to do on its own before a person has to say yes? Match the answer to the risk and reversibility of the specific action, not to how confident the model's text sounds, because confident wording and a correct action are two different things, measured two different ways.

Three levels cover most of what you'll build. Suggest: the system proposes, a person decides. Act with confirmation: it executes once a person approves that specific action. Act and report: it executes on its own and tells you afterward. Module 4's decision models give you a principled way to pick between these per action, since a calibrated probability is a reasonable input to "ask or just act"; an uncalibrated one is a confident-sounding guess wearing the same clothes.

Three more habits round it out. Trust calibration: show your work and your sources, say plainly when you're unsure, and watch for both over-trust (a user who stops checking) and under-trust (a user who re-verifies everything and gets none of the speed back). Recoverability: confirm before anything irreversible, offer an undo where one is possible, and keep an activity log written in plain language, not log-level jargon, since the person reading it afterward is not you. Failure UX: when the system can't finish, hand off to a human or a manual path instead of a dead end.

The blameless postmortem

Things will break in the first week. The professional response is a written, blameless postmortem, the practice described in the Postmortem Culture chapter of Google's Site Reliability Engineering (O'Reilly, 2016): describe what happened and how the system allowed it, never who did it. Blame teaches people to hide failures; a blameless review teaches the system to catch them.

The structure is short: a timeline, a root cause, what you changed, how you know it's fixed, and follow-ups. The root cause uses the same seven classes as Module 5's harness table (missing context, wrong tool, bad output, repeated loop, unsafe action, lost decision, unknown), and the fix is held to the same standard: a change to the system, plus a case added to the golden set so the failure cannot quietly return. "We rewrote the prompt" isn't a fix; it is a patch.

Telling the story

A 60-second demo has to earn its seconds: the problem in 8, the real app doing a real task in 30, how it's built in 12, the numbers in 8, and where to try it in 2. Write the script first and time it, because people read aloud at about 150 words a minute and a draft that feels short almost never is. Show the app working on the problem, not slides about it.

For interviews, the same material compresses into four sentences: the problem and who had it, one decision you defended with numbers, one failure you diagnosed and fixed, and what you would do next. If you can say those four things with real numbers, the project has done its job. Each of them comes from work you already did in Modules 3 to 6.

Run before every push; add it to CI.""" import re, subprocess, sys from pathlib import Path PATTERNS = { "OpenAI-style key": re.compile(r"sk-(?:proj-)?[A-Za-z0-9_-]{20,}"), "Anthropic-style key": re.compile(r"sk-ant-[A-Za-z0-9_-]{20,}"), "Google API key": re.compile(r"AIza[0-9A-Za-z_-]{30,}"), "GitHub token": re.compile(r"gh[pousr]_[A-Za-z0-9]{30,}"), "AWS access key id": re.compile(r"AKIA[0-9A-Z]{16}"), "private key block": re.compile(r"-----BEGIN (?:RSA |EC |OPENSSH )?PRIVATE KEY-----"), "key assigned in code": re.compile(r"""(?i)(?:api[_-]?key|secret|token|password)\s*[:=]\s*["'][A-Za-z0-9_\-]{16,}["']"""), } FORBIDDEN_NAMES = {".env", "id_rsa", "id_ed25519"} def tracked_files(root="."): try: out = subprocess.run(["git", "ls-files"], capture_output=True, text=True, cwd=root, check=True).stdout.split("\n") return [Path(root) / f for f in out if f] except Exception: return [p for p in Path(root).rglob("*") if p.is_file() and ".git" not in p.parts and ".venv" not in p.parts] def scan(root="."): problems = [] for path in tracked_files(root): if path.name in FORBIDDEN_NAMES: problems.append(f"{path}: this file should never be committed") continue try: text = path.read_text(errors="ignore") except Exception: continue for label, pat in PATTERNS.items(): for m in pat.finditer(text): line = text.count("\n", 0, m.start()) + 1 problems.append(f"{path}:{line}: looks like a {label}: {m.group()[:8]}...") return problems if __name__ == "__main__": problems = scan(sys.argv[1] if len(sys.argv) > 1 else ".") print("\n".join(problems) if problems else "no secrets found") if problems: print("\nIf this is real: rotate the key now (a pushed key is a leaked key, even if you delete the commit), " "then remove it from the file and read it from the environment.") sys.exit(1 if problems else 0)

    """Smoke test a running service. Usage: python service/smoke.py https://your-app.example.com Measures cold-start time, warm latency, and proves the rate limiter works.""" import statistics, sys, time import httpx base = sys.argv[1].rstrip("/") QUESTION = "How long is the warranty on the Larkfield Delta Sensor?" c = httpx.Client(timeout=60) print("health :", c.get(f"{base}/health").json()) t0 = time.time() while True: # the first request on a sleeping free-tier host can take a minute r = c.get(f"{base}/ready") if r.status_code == 200: break if time.time() - t0 > 180: sys.exit("never became ready within 3 minutes") time.sleep(2) print(f"ready : after {time.time() - t0:.1f}s (cold start, including loading the index)") lat = [] for _ in range(4): # stay under the rate limit while measuring warm latency t = time.perf_counter() r = c.post(f"{base}/ask", json={"question": QUESTION}) lat.append((time.perf_counter() - t) * 1000) assert r.status_code == 200, r.text print(f"warm : median {statistics.median(lat):.0f} ms over {len(lat)} requests, answer: {r.json()['answer'][:70]!r}") codes = [c.post(f"{base}/ask", json={"question": QUESTION}).status_code for _ in range(25)] print("burst :", "rate limiter returned 429 after", codes.index(429) + 1, "more requests" if 429 in codes else "NEVER FIRED") print("bad body:", c.post(f"{base}/ask", json={"question": "x"}).status_code, "(expect 422, or 429 if you are still rate limited)") sys.exit(0 if 429 in codes else 1)

    """Turn the service's request log into the numbers a README needs: latency percentiles, cost, errors. Usage: python service/prod_report.py requests.log (pipe your host's log export into a file first)""" import json, statistics, sys from pathlib import Path sys.path.insert(0, "service") from costs import PRICES, cost_usd rows = [] for line in open(sys.argv[1]): try: e = json.loads(line) except ValueError: continue # hosts mix their own lines into the log; skip them if "path" in e and e["path"] not in ("/health", "/ready"): rows.append(e) def pct(xs, p): xs = sorted(xs) return xs[min(len(xs) - 1, int(round(p / 100 * (len(xs) - 1))))] summary = {} for kind in ("ask", "research"): rs = [r for r in rows if r.get("kind") == kind and r["status"] == 200] if not rs: continue ms = [r["ms"] for r in rs] hits = sum(bool(r.get("cached")) for r in rs) miss = [r for r in rs if not r.get("cached")] cost = [cost_usd(r["input_tokens"], r["output_tokens"]) for r in miss] print(f"/{kind}: {len(rs)} ok requests, p50 {pct(ms, 50):.0f} ms, p95 {pct(ms, 95):.0f} ms, " f"cache hits {hits}/{len(rs)}") summary[kind] = {"requests": len(rs), "p50_ms": round(pct(ms, 50)), "p95_ms": round(pct(ms, 95)), "cache_hit_rate": round(hits / len(rs), 3)} if PRICES == (0.0, 0.0): print(" cost: fill in service/costs.py") else: summary[kind]["cost_per_miss_usd"] = round(statistics.mean(cost), 6) print(f" mean cost per cache-miss request: ${statistics.mean(cost):.5f}") errors = [r for r in rows if r["status"] >= 500] limited = [r for r in rows if r["status"] == 429] summary["error_rate_5xx"] = round(len(errors) / len(rows), 4) Path("service/prod_metrics.json").write_text(json.dumps(summary, indent=1)) print(f"errors (5xx): {len(errors)}/{len(rows)} rate limited (429): {len(limited)}/{len(rows)}")

    """Time a spoken demo script before you record it. People read aloud at about 150 words a minute (2.5 a second). Each '## Beat (Ns)' heading gives that beat's time budget. Usage: python checks/script_timer.py demo_script.md""" import re, sys from pathlib import Path WORDS_PER_SECOND = 2.5 beats, total_budget, total_est = [], 0, 0.0 current = None for line in Path(sys.argv[1]).read_text().splitlines(): m = re.match(r"##\s+(.*?)\s*\((\d+)\s*s\)\s*$", line) if m: current = {"name": m.group(1), "budget": int(m.group(2)), "words": 0} beats.append(current) elif current and line.strip() and not line.startswith("#"): current["words"] += len(re.findall(r"\b[\w'-]+\b", re.sub(r"\[.*?\]", "", line))) # [on screen: ...] cues aren't spoken if not beats: sys.exit("no '## Name (Ns)' headings found") ok = True for b in beats: est = b["words"] / WORDS_PER_SECOND flag = "" if est <= b["budget"] else " TOO LONG: cut " + str(int(b["words"] - b["budget"] * WORDS_PER_SECOND + 0.99)) + " words" ok &= est <= b["budget"] total_budget += b["budget"]; total_est += est print(f"{b['name']:16s} {est:5.1f}s of {b['budget']:2d}s ({b['words']} words){flag}") print(f"{'total':16s} {total_est:5.1f}s of {total_budget}s") sys.exit(0 if ok and total_est <= 60 else 1)

  1. Create service/activity.py. The three levels match this module's Concepts section exactly: suggest proposes and stops, confirm would wait for a second, explicit approval before acting (simulated here with a flag, since this service has no UI to click "approve" in), and act executes immediately and logs it afterward. The log is written as plain sentences, not JSON keys, because the person reading it back is the point, not a grep target.
    """An autonomy gate and a human-readable activity log for the agent endpoint. The three levels match this module's Concepts section: suggest, act with confirmation, act and report.""" import json, time from pathlib import Path ACTIVITY_LOG = Path("service/activity.jsonl") def log_activity(user, level, action, detail, executed): with open(ACTIVITY_LOG, "a") as f: f.write(json.dumps({"ts": time.time(), "user": user, "autonomy": level, "action": action, "detail": detail, "executed": executed}) + "\n") def gate(level, action, detail, do_action, confirmed=False, user="demo"): """suggest: proposes only, never executes. confirm: executes only if the caller already passed confirmed=True (a real UI would ask first, then resend the request). act: executes immediately and the log is how you find out about it afterward.""" if level == "suggest" or (level == "confirm" and not confirmed): log_activity(user, level, action, detail, executed=False) return {"proposed": detail, "executed": False, "note": "awaiting your confirmation"} result = do_action() log_activity(user, level, action, detail, executed=True) return {"result": result, "executed": True} def read_activity(n=20): """Plain-language lines, not raw JSON, for a non-engineer reading what the system did.""" if not ACTIVITY_LOG.exists(): return ["(nothing logged yet)"] lines = [json.loads(l) for l in ACTIVITY_LOG.read_text().splitlines()[-n:]] out = [] for e in lines: when = time.strftime("%H:%M:%S", time.localtime(e["ts"])) did = "did" if e["executed"] else "proposed, but did not do" out.append(f"[{when}] at autonomy level '{e['autonomy']}', the system {did}: {e['detail']}") return out

Project · Every project on GitHub

Ship every project from this course, not only the best one. Each gets a README a stranger can follow, numbers its tools measured, and a check that keeps it honest.

  1. Give every project folder (and the repo root) its own README from Lab 2's template, with a Quick start of about ten commands at most. Where a project has no eval or live numbers, delete those rows from its table instead of leaving them unmeasured; a missing claim is better than an invented one.
  2. Run the stranger test on each project. This script clones the repo into an empty folder, creates a fresh virtual environment, runs your Quick start commands exactly as written with none of your API keys or settings available, and times the whole thing. It fails if any command fails or if the total passes ten minutes.
    """The stranger test: clone the repo into an empty folder, make a new virtual environment, run the README's Quick start commands exactly as written, and time it. Usage: python checks/fresh_clone_test.py <repo path or URL>""" import os, re, subprocess, sys, tempfile, time from pathlib import Path LIMIT_SECONDS = 600 repo = sys.argv[1] work = Path(tempfile.mkdtemp(prefix="fresh_clone_")) t_all = time.time() subprocess.run(["git", "clone", "--quiet", repo, str(work / "repo")], check=True) checkout = work / "repo" subprocess.run([sys.executable, "-m", "venv", str(work / "venv")], check=True) bindir = work / "venv" / ("Scripts" if os.name == "nt" else "bin") env = {**os.environ, "PATH": f"{bindir}{os.pathsep}{os.environ['PATH']}", "VIRTUAL_ENV": str(work / "venv")} env.pop("PYTHONPATH", None) # nothing from your own machine may leak in for k in [k for k in env if k.endswith("_API_KEY")]: env.pop(k) # and none of YOUR keys: a stranger has none readme = (checkout / "README.md").read_text() quick = re.search(r"##\s+Quick start\s*\n(.*?)(?=\n##\s|\Z)", readme, re.S) if not quick: sys.exit("README has no '## Quick start' section") commands = [l.strip() for blk in re.findall(r"```(?:bash|sh|shell)?\n(.*?)```", quick.group(1), re.S) for l in blk.splitlines() if l.strip() and not l.strip().startswith("#")] failed = None for cmd in commands: t = time.time() r = subprocess.run(cmd, shell=True, cwd=checkout, env=env, capture_output=True, text=True) print(f"{'ok ' if r.returncode == 0 else 'FAIL'} {time.time() - t:6.1f}s {cmd}") if r.returncode != 0: failed = (cmd, (r.stderr or r.stdout)[-400:]) break total = time.time() - t_all print(f"\ntotal: {total:.0f}s (limit {LIMIT_SECONDS}s) folder: {work}") if failed: print(f"\nA stranger would be stuck here:\n {failed[0]}\n{failed[1]}") sys.exit(1 if failed or total > LIMIT_SECONDS else 0)

What we tested, and what only you can

The tooling in this lesson was run and tested: the web service (nine tests plus a live smoke run), the secrets scanner, the production-metrics report, the README checker in all its failing and passing states, the demo-script timer, the pitch checker, and the stranger test against a small sample repository, including a deliberately broken Quick start. The README tooling and the stranger test were not run against your project, and nothing here was deployed to a real host, so cold-start time, memory use, real latency and cost per request are yours to measure. Done when:

  • A stranger can run each project from its README in under 10 minutes, and the stranger test passes.
