Module 0 · Setup

Setup and the Course Repo

This module doesn't ship a feature — it builds the infrastructure every later module stands on. The folder layout, the .env convention, and above all shared/llm_client.py (one function that calls any provider and logs every call) aren't throwaway setup steps; they're the shared architecture that Module 1's cost meter, Module 4's budget alerts, and every project after that will import and extend instead of rebuilding. Get this module right and the rest of the course gets easier, not harder.

Everything below assumes Python 3.11+ and a terminal. Unless a step says otherwise, run every command from the ai-beyond-fundamentals/ repo root you create in Lab 1, with its venv activated — that's what makes relative paths like chatbot/three_providers.py resolve correctly. Work through the concepts once, then do the labs in order — each one builds on the last.

Concepts

Keep API keys in environment files, never in code

A provider API key is a bearer credential: whoever holds the string can spend money on your account. If it's typed directly into a .py file, it ships the moment that file is committed to git — including to a public GitHub repo, a screen share, or a zip you email someone. Leaked keys get scraped by bots within minutes and run up real charges.

The fix is a .env file at the repo root holding NAME=value pairs, loaded at runtime by a library like python-dotenv. The file never gets committed — it's listed in .gitignore before it ever holds a real key. Collaborators instead get a .env.example with the same variable names and blank or placeholder values, committed normally, so they know what to fill in without ever seeing yours.

Python environments with venv and pip, in a monorepo layout

venv is Python's built-in tool for creating an isolated environment so this project's packages don't collide with anything else installed on your machine. pip installs into it.

If you write anthropic in a requirements file with no version attached, pip install grabs whatever the newest release happens to be on the day it runs — today that might work, three months from now a new major version could change the SDK's method names and break every lab that imports it, with no code change on your end to explain why. "Pinning" means locking each package to the exact version number you tested with, so installing never silently changes what you're running.

Neither venv nor pip tracks those exact versions for you automatically (this is what uv or poetry would do instead). You do it by hand with pip freeze, which inspects everything currently installed in the active environment and prints each package with an exact == version:

$ pip freeze anthropic==2.3.0 openai==3.37.0 google-genai==2.33.0 python-dotenv==1.2.4 ...

Redirecting that output into requirements.txt and committing the file turns it into the pin list. From then on, pip install -r requirements.txt installs exactly those versions, so your setup, your collaborator's, and the one this checklist describes all run identical code.

Prefer uv or poetry? This course uses venv and pip because they ship with Python and need nothing extra installed. uv and poetry are popular alternatives that create the environment, install packages and record exact versions in a lockfile for you. If you already use one, it works for every lab: translate the install commands and skip the manual pip freeze step.

A monorepo here just means one repository, one pyproject.toml, and one lockfile for every project this course builds — the chatbot, the extraction tool, the RAG app, the eval suite, the agent, and the RAG-vs-fine-tune comparison — each in its own folder, plus a shared/ folder for code every project reuses. One environment to install instead of seven, and one place to fix a dependency problem instead of seven.

A shared client wrapper that logs every call

Every lab from here on calls a model. If each lab calls the provider SDK directly, cost and latency tracking has to be rebuilt seven times — or, more likely, never gets built at all. Instead, this module produces one function, call(prompt, model), that every later lab imports from shared/. It hides which provider you're talking to and silently appends a row — model, tokens in, tokens out, milliseconds, dollars — to a shared log file on every call.

That log file is what makes Module 1's cost meter, Module 4's budget alerts, and Module 4's regression tests possible without extra plumbing. You're building the instrument panel before you need to read it.

  1. Create the repo and one virtual environment at the root — every project folder below shares it, so you activate it once per terminal session, not once per folder.
    mkdir ai-beyond-fundamentals cd ai-beyond-fundamentals
    macOS / Linuxpython3 -m venv .venv source .venv/bin/activate
    Windows (PowerShell)python -m venv .venv .venv\Scripts\Activate.ps1
    What does python3 -m venv .venv do?

    It creates an isolated Python environment inside a folder named .venv. Breaking the command down:

    • python3 runs your system's Python interpreter.
    • -m venv tells Python to run a standard-library module as a program. The module is venv, which ships with Python, so there is nothing to install.
    • .venv is the folder where the new environment goes. The leading dot hides it in Finder and in a plain ls; that is just convention.

    What ends up inside .venv/:

    • bin/python, a private link to the interpreter. This is what runs once you activate.
    • bin/pip, an installer that puts packages in .venv/lib/.../site-packages instead of your system Python.
    • bin/activate, the script source .venv/bin/activate runs. It puts .venv/bin first on your PATH, so typing python or pip now means the private ones.

    Why bother: packages installed here never touch your system Python or other projects, other projects can't break this one by upgrading a shared package, and the pinned versions in requirements.txt stay exactly what you tested with.

    Creating the venv does not activate it. Run source .venv/bin/activate in every new terminal. You'll see (.venv) at the start of your prompt when it's on. Check with which python: the path should end in .venv/bin/python, not /usr/bin/python3. .venv is listed in .gitignore because it is large and machine-specific; anyone else rebuilds it from requirements.txt.

    macOS / Linuxmkdir -p shared chatbot extraction rag evals agent ragvsfinetune
    Windows (PowerShell)mkdir shared, chatbot, extraction, rag, evals, agent, ragvsfinetune
    Why does macOS use mkdir -p but PowerShell doesn't?

    They are two different programs that happen to share a name.

    macOS / Linux: mkdir -p

    • mkdir is a small program from the Unix toolset, and it takes flags.
    • By default it makes one folder at a time, and it errors if the parent is missing or the folder already exists.
    • -p (“parents”) changes that in two ways: it creates any missing parent folders, and it does not error if the folder already exists.
    • -p is also what makes listing several folders in one command work, as this step does.

    Windows PowerShell: mkdir shared, chatbot, ...

    • In PowerShell, mkdir is a built-in function that wraps New-Item -ItemType Directory.
    • That command already creates missing parents and already tolerates existing folders, so there is nothing for a -p flag to turn on.
    • PowerShell takes multiple names as a comma-separated list, because it passes them as a list of values rather than as separate words.

    One more difference: PowerShell commands usually take full-word parameters like -Path or -Force, not single-letter Unix flags. Typing mkdir -p in PowerShell would likely fail or be read as an abbreviated parameter name.

Project

Project · One client, four providers

Combine the four labs into one file, shared/llm_client.py: a single call(prompt, model) function that looks up the provider for a given model name in a config file, dispatches to the right SDK, times the call, computes real cost, and logs it through log_call from Lab 4. Worth knowing

You just hand-built a small version of what LiteLLM is as a library: one call() across 100+ providers, with cost tracking, retries and logging already built in. A real production codebase would likely reach for LiteLLM (or something like it) instead of this file. You built it by hand here so that choice is a shortcut once you understand what it's hiding, not a black box you're trusting blind.
