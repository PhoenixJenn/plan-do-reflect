Module 2 · Prompting & Reliability

Prompting & Reliability

Module 1 taught you what a call costs and how long it takes. This module is about whether you can trust what comes back — getting structured data you can parse, catching the model when it's about to guess, and treating a prompt as something you version and measure rather than something you tweak until it feels right.

Fair warning going in: several of this module's labs were built expecting classic failure modes (sloppy JSON, hallucinated facts on absent topics) that turned out not to reproduce with current mid-tier models. Rather than fake those failures, the labs below report what actually happened and redesign around the real finding. That's it's own lesson — test your assumptions about model behavior instead of inheriting them.

Concepts

System prompts and few-shot examples

A system prompt sets standing behavior before the conversation starts. Few-shot examples go further: instead of just describing the task, you show 2–5 worked examples of input → correct output directly in the prompt, and the model pattern-matches onto them. More examples isn't automatically better — Lab 1 below measures this directly rather than assuming it.

Choosing good examples matters more than choosing more of them: cover the edge cases and boundary confusions your task actually has, not just the easy, obvious cases.

Step-by-step reasoning

Asking a model to reason through a problem before answering ("think step by step," or a model's own built-in extended thinking) can improve accuracy on multi-step problems — arithmetic, logic, multi-hop questions — by giving it room to work instead of forcing an immediate answer. It costs real tokens (and therefore real money and latency) for every step reasoned through, and on simple tasks it can add cost with no accuracy benefit at all.

Advice on when reasoning helps differs by model family and changes as models improve — the only reliable way to know is to test it on your own task, not memorize a rule from last year.

Structured output: schemas, Pydantic, validation, and retry

Asking a model for JSON and getting back something your code can actually parse are two different problems. A Pydantic model defines the exact shape you expect; after the call, you parse the raw text and validate it against that shape, catching both malformed JSON and the right JSON shape with wrong types.

The real failure mode worth planning for isn't sloppy formatting — current mid-tier models are quite disciplined about that. It's truncation: the model's JSON gets cut off mid-object because max_tokens wasn't enough for a longer or more complex response. That failure is deterministic at a fixed budget, so retrying with the identical budget just fails again — the retry has to increase the budget, not just try again. Lab 2 demonstrates this directly.

Tool calling: request, result, follow-up

Tool calling is a three-step loop, not a single call. You send the model a list of tools (name, description, a JSON schema for its arguments); the model's response can ask to call one by name with specific arguments instead of answering directly; you run that tool in your own code and send the result back as a new message; the model then either answers using that result or asks for another tool call. A multi-step task (look up a rate, then do arithmetic with it) can chain several of these rounds before producing a final answer — Lab 3 logs every round so the loop is visible instead of hidden inside the SDK.

Grounding and hallucination — what it actually buys you now

The classic advice is: require the model to quote or cite the source document, and to explicitly say "not found" rather than guess, to stop it from inventing facts about topics the document never covers. Testing that directly in Lab 4 (across plain questions, false-presupposition questions, zero-instruction prompts, and questions about adjacent-but-uncovered topics) found that a current mid-tier model didn't invent a single fact in any condition, grounding rule or not.

What the grounding rule actually changed was something else entirely: whether a correct answer came with a verifiable quote pointing back to its source. Without the rule, 1 answer out of 8 included an exact quote from the document; with it, all 8 did. The value shifted from "stops fabrication" to "makes correct answers auditable" — still a real, valuable property, just not the one the rule was originally sold on.

Chain-of-Verification

A four-step pattern for catching a model's own mistakes before they reach the user: draft an initial answer, generate a short list of fact-check questions against that draft, answer those check questions independently (often more reliable than the original pass, since each question is narrower), then revise the draft using anything the checks turned up. It costs 3–4x the calls of a single pass, so it's worth reserving for answers where being wrong is expensive — not a default for every request.

Prompt versioning and A/B tests

Treat a prompt the way you'd treat code: store each version as its own file, run both versions against the identical set of inputs, and compare with real numbers rather than a gut feeling about which "reads better." Lab 5 found something worth internalizing: a prompt change can fix the specific error it targeted while leaving aggregate accuracy completely flat, because it trades that mistake for a different one elsewhere. Look at which errors changed, not just whether the overall score moved.

Hands-on Labs

  1. Create chatbot/tickets.py with 50 hand-labeled support tickets, 10 per category, across 5 categories: Billing, Bug Report, Feature Request, Account Access, How-To Question. Also build two example pools — the first 2 and first 5 tickets of each category — for the few-shot conditions.
    # chatbot/tickets.py (excerpt -- 50 tickets total in the real file) CATEGORIES = ["Billing", "Bug Report", "Feature Request", "Account Access", "How-To Question"] TICKETS = [ ("I was charged twice for my subscription this month, can you refund the duplicate?", "Billing"), ("How do I update the credit card on file for my account?", "Billing"), ("The export button does nothing when I click it, no error, no download.", "Bug Report"), # ... 47 more, 10 per category ] def _examples_per_category(n): out = [] for cat in CATEGORIES: out.extend([t for t in TICKETS if t[1] == cat][:n]) return out FEW_SHOT_2 = _examples_per_category(2) # 10 examples total FEW_SHOT_5 = _examples_per_category(5) # 25 examples total
  2. Create chatbot/zero_shot_few_shot.py. One function builds the system prompt (category list, plus any examples formatted as Ticket/Category pairs); one classifies a single ticket; one runs all 50 and reports accuracy plus the first few wrong answers.
    import os from dotenv import load_dotenv load_dotenv() from openai import OpenAI from tickets import CATEGORIES, TICKETS, FEW_SHOT_2, FEW_SHOT_5 client = OpenAI(api_key=os.environ["OPENAI_API_KEY"]) def build_system_prompt(examples): prompt = ("Classify each support ticket into exactly one of these categories: " + ", ".join(CATEGORIES) + ". Reply with only the category name, nothing else.") if examples: prompt += "\n\nExamples:\n" for text, label in examples: prompt += f"Ticket: {text}\nCategory: {label}\n\n" return prompt def classify(ticket_text, system_prompt): resp = client.chat.completions.create( model="gpt-4.1-mini", max_tokens=10, messages=[{"role": "system", "content": system_prompt}, {"role": "user", "content": f"Ticket: {ticket_text}\nCategory:"}], ) return resp.choices[0].message.content.strip() def run(label, examples): system_prompt = build_system_prompt(examples) correct = 0 for text, true_label in TICKETS: if classify(text, system_prompt) == true_label: correct += 1 print(f"{label}: {correct}/{len(TICKETS)} correct ({correct/len(TICKETS):.0%})") return correct / len(TICKETS) if __name__ == "__main__": run("0-shot", []) run("2-shot", FEW_SHOT_2) run("5-shot", FEW_SHOT_5)
  3. Run it. All 150 calls (50 tickets × 3 conditions) take a couple of minutes.
    python chatbot/zero_shot_few_shot.py
Check: our own run came back 0-shot 90%, 2-shot 94%, 5-shot 92%. Few-shot helped over zero-shot, but more examples (5 vs. 2) didn't keep improving it — and at 50 tickets, a 1-ticket swing is well within noise, worth remembering before reading too much into small differences. The one consistent, non-noisy finding across all three conditions: "How do I update the credit card on file?" kept getting classified as How-To Question instead of Billing — a real category-boundary ambiguity (it's phrased as a how-to question about a billing topic), not something more examples fixed.   4. Now write the retry logic the right way. A truncation failure at a fixed max_tokens is deterministic — retrying with the same budget fails again every time. Each retry has to raise the budget instead.
    from pydantic import ValidationError def extract_with_retry(invoice_text, max_attempts=3, start_tokens=80): max_tokens = start_tokens for attempt in range(max_attempts): resp = client.chat.completions.create( model="gpt-4.1-mini", max_tokens=max_tokens, messages=[{"role": "system", "content": SCHEMA_PROMPT}, {"role": "user", "content": invoice_text}], ) raw = resp.choices[0].message.content try: return Invoice(**json.loads(raw)), attempt except (json.JSONDecodeError, ValidationError): max_tokens *= 2 return None, max_attempts
Check: in our own run, the 5-line-item invoice failed at max_tokens=250 and 150 (cut off one token before the closing brace at 150), succeeded at 80 only after this exact invoice got lucky with a shorter response — the honest takeaway is that the failure point depends on both the invoice's complexity and the model's specific phrasing that run, not a fixed number you can hardcode. extract_with_retry starting at start_tokens=60 against this same invoice needed exactly 2 attempts (60 → 120 tokens) to succeed — confirm that on your own machine before trusting it.
  1. Create chatbot/tool_calling.py. Define both tools' schemas and the (fake, fixed-table) functions that actually run them.
    import os from dotenv import load_dotenv load_dotenv() from anthropic import Anthropic client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"]) EXCHANGE_RATES = {"USD_EUR": 0.92, "USD_GBP": 0.79, "EUR_USD": 1.09, "GBP_USD": 1.27} TOOLS = [ {"name": "calculator", "description": "Evaluate a basic arithmetic expression, e.g. '12.5 * 4 + 30'.", "input_schema": {"type": "object", "properties": {"expression": {"type": "string"}}, "required": ["expression"]}}, {"name": "exchange_rate", "description": "Look up the exchange rate between two currencies.", "input_schema": {"type": "object", "properties": { "from_currency": {"type": "string"}, "to_currency": {"type": "string"}}, "required": ["from_currency", "to_currency"]}}, ] def run_tool(name, tool_input): if name == "calculator": return str(eval(tool_input["expression"])) if name == "exchange_rate": key = f"{tool_input['from_currency']}_{tool_input['to_currency']}" return str(EXCHANGE_RATES.get(key, f"No rate available for {key}")) return f"Unknown tool: {name}"
  2. Write the loop: call the model, check whether it asked for a tool, run that tool yourself, send the result back as a new message, and repeat until it answers in plain text instead.
    def chat_with_tools(user_message, max_rounds=5): messages = [{"role": "user", "content": user_message}] print(f"User: {user_message}") for round_num in range(max_rounds): resp = client.messages.create(model="claude-sonnet-5", max_tokens=500, tools=TOOLS, messages=messages) tool_uses = [b for b in resp.content if b.type == "tool_use"] if not tool_uses: final_text = next((b.text for b in resp.content if b.type == "text"), "") print(f"Claude: {final_text}") return final_text messages.append({"role": "assistant", "content": resp.content}) tool_results = [] for tool_use in tool_uses: result = run_tool(tool_use.name, tool_use.input) print(f" [round {round_num}] {tool_use.name}({tool_use.input}) -> {result}") tool_results.append({"type": "tool_result", "tool_use_id": tool_use.id, "content": result}) messages.append({"role": "user", "content": tool_results}) if __name__ == "__main__": chat_with_tools("I'm buying something that costs 80 EUR. How much is that in USD, " "and if I buy 3 of them, what's the total in USD?")
  3. Run it and read the round-by-round trace.

Project · Invoice PDF to clean JSON

Lab 2 built the schema + retry pattern on one invoice. This project runs it for real at 20-invoice scale, against actual PDF files, with a step this module's earlier labs skipped entirely: converting a PDF into something an LLM can reliably read in the first place.

Why PDF-to-Markdown first, not raw text

A naive pypdf-style text dump reads a PDF's text in element position order with no concept of a table — on a real multi-column invoice, that can scramble or interleave columns into unusable text. A converter that targets Markdown instead (we tested pymupdf4llm) detects the table and emits it as an actual Markdown table, which an LLM parses far more reliably. This is standard practice in real document-extraction pipelines (Microsoft's markitdown, Docling, and commercial tools like LlamaParse all target Markdown as the intermediate format specifically for this reason) — not something invented for this course. pymupdf4llm is dual-licensed AGPL-3.0 or a paid commercial license from Artifex; fine for an open project like this one, but check that license before shipping it inside anything closed-source.
