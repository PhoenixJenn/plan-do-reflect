AI Beyond Fundamentals

A hands-on course for engineers who can already call a model and want to build AI systems that hold up in production.

Try It

Why It Matters

AI Fundamentals teaches you to use AI. This course teaches you to build with it. The gap between a demo that works once and a system people rely on is almost never the model. It is retrieval that finds the right passage, evals that catch regressions, guardrails that stop bad actions, and a harness that keeps an agent on track. Those are engineering skills, and they can be learned by building.

What You'll Be Able to Do

  • Choose a model, prompt it reliably, and explain its cost and latency per call
  • Build a production-grade RAG pipeline over messy documents and measure retrieval quality
  • Write an eval suite that runs in CI and blocks regressions
  • Build an agent with tools, limits and human approval, starting from a raw API loop
  • Defend architecture choices: RAG vs fine-tuning, workflow vs agent, big vs small model
  • Ship two deployed apps with a README that shows eval, cost and latency numbers

"Humans steer. Agents execute."

OpenAI, Harness engineering

How the Course Works

Every module follows the same loop as the rest of this site. Plan with a short concept lesson. Do three to six guided labs, each with starter code and a checkpoint test. Reflect by shipping a module project and writing down what broke and how you fixed it.

All labs use one shared document collection (public company filings, meeting minutes, or product manuals all work), so you build one system that grows each module instead of seven throwaway demos. You need Python, Git, and comfort calling a REST API. No machine learning background is assumed.

Retrieval-augmented generation (RAG) has two halves. Documents are processed once and stored in an index. Every question then runs through search, and the best passages are handed to the model along with the question.

What you'll learn

  • Digitizing documents: OCR for scans, text extraction for native PDFs
  • Layout parsing that keeps tables, headers and reading order intact
  • Chunking strategy per document type, including chunk size and overlap
  • Vector indexes: HNSW (fast and accurate, memory-heavy), IVF (clustered, cheaper at scale), PQ (compressed, smaller and less exact)
  • Embedding models and vector databases
  • Hybrid search: keyword scores (BM25) plus vector scores, merged with reciprocal rank fusion
  • Splitting multi-part questions and filtering by metadata such as date or source
  • Reranking, then measuring retrieval with recall@k against labeled questions

Hands-on labs

  1. Naive baseline. Build the simplest RAG over the course documents. Write 30 questions with the correct source page and record recall@5. Every later lab has to beat it.
  2. Parsing bake-off. Extract 5 hard PDFs (one scanned, two table-heavy) with a basic extractor and a layout-aware parser. Note what each one lost.
  3. Chunking experiment. Compare three chunking strategies on the same 30 questions.
  4. Index types. Build HNSW and IVF-PQ indexes on 100,000 synthetic vectors. Measure build time, memory, speed and recall.
  5. Hybrid search. Add keyword search and fuse the results. Find the questions it fixes, usually exact terms like IDs and product codes.
  6. Rerank and filter. Retrieve 20, rerank to 5, and add a metadata filter. Record final recall and the added latency.
Project · Chat with 100 messy PDFs

A deployed chat app with citations that link to the source page, a semantic cache, and a page showing recall before and after each upgrade.

Done when: citations open the right page, recall beats the baseline with the biggest win identified, and cost and latency per question are reported.

Harness engineering: fix the system, not the prompt

The model is only the reasoning engine. It can suggest the next action, but it cannot create a reliable operating environment by itself. The harness decides what the model can see, what it can touch, what survives between sessions, what counts as evidence, and when the run must stop.

Model

Reasons and proposes actions.

Harness

  • Selects context
  • Exposes tools
  • Stores state
  • Enforces permissions
  • Checks results
  • Records traces
  • Recovers from failure

The prompt is one component inside this system, and the model is another. The product is what happens when every surrounding component works together.

"Prompt engineering improves the instruction. Harness engineering improves the conditions under which the instruction is executed."

rari, Harness Engineering

Put a model in a chat box and it answers questions. Put the same model in a repository with terminal access, tests, browser tools, project memory and a review loop, and it can ship software. The weights did not change. The harness did.

The seven jobs of a production harness

  1. Turn the request into a contract. Before acting, write down the goal, inputs, expected output, constraints, and what "done" means. Without it, the agent can finish a different job and still declare success.
  2. Give the agent a map. A small root guide that points to architecture, testing, product and security notes. A map preserves context, while a giant manual consumes it.
  3. Expose the right tools in the right environment. Every tool needs a clear purpose, predictable output, an explicit failure state, and a permission boundary. Reading files can be allowed by default; deploying or deleting data requires approval.
  4. Externalize memory into durable state. The conversation is not the system of record. Store decisions, artifacts, failures and open risks in a file, so the next session inherits the work, not a lossy retelling of the chat.
  5. Add sensors before adding autonomy. Tests, linters, screenshots, logs and schema checks turn vague quality into evidence. The model creates an artifact, the environment produces evidence about it, and the harness decides whether that is enough to continue.
  6. Enforce permissions outside the model. The model suggests, a policy checks, a tool executes. Don't ask one probabilistic system to invent the plan, approve the risk and carry out the side effect.
  7. Record traces and recover locally. Every run leaves a readable trail: the request, context selected, tool calls, state changes, checks, retries, cost and a rollback point. Without traces, failure is a mystery. With them, it is input for the next improvement.

Failure should upgrade the system

When an agent fails, the instinct is to rewrite the prompt, switch models, or add context. The failures usually come back. The better move is to name the class of failure and change the harness. The immediate patch fixes one run. The harness change improves every run after it.

Failure you seeHarness fix
Missing contextGive the agent a map of its workspace or a retrieval rule
Wrong toolImprove the tool description or add routing
Bad outputAdd a validator or a stricter output contract
Repeated loopCap retries and escalate to a human
Unsafe actionAdd a permission gate
Lost decisionWrite it to durable state
Unknown failureAdd tracing and capture evidence

Adapted from rari, Harness Engineering.

Brain. The model that reasons. It should not also be the filesystem, the permission system, the memory store and the audit log.

Hands. The sandbox and tools that act, each behind its own permissions.

History. An append-only record of what happened. Keep the whole run, not only the final answer. It is what makes debugging and evals possible.

Instructions should become infrastructure

Rules kept only in prose get read, then eventually ignored. Encode each important rule twice: once as guidance the agent can understand, and once as a mechanical check it cannot bypass.

Example

Guide: "UI code may not query the database directly."

Check: the linter fails when UI code imports the database layer.

The guide explains the reason, and the check enforces the boundary. A past failure becomes a permanent fix. The next agent doesn't need to remember the incident, because the harness remembers it.

The loop belongs to the harness

"Keep trying until it works" is not a control system. A useful loop has evidence, a retry cap, a budget and an escalation path: build, verify, record the gap, and try again up to three times before asking a human. The model decides how to repair the gap. The harness decides whether another attempt is allowed.

Give every run a change receipt

Keep more than the final output. Save a compact receipt of how it was produced: context sources, model route, tools used, test results, human corrections, retries, cost, the accepted artifact and a rollback point. Receipts make model upgrades comparable, regressions attributable and audits possible.

Start with the smallest harness that closes the loop

LevelWhat it adds
0Prompt and model
1A project guide and tools
2Structured state, tests and a bounded loop
3Permissions, traces, recovery and human approval gates

Move up a level only when the task earns it. A short, low-risk task may need one prompt and one review. A six-hour run that edits files, reaches the network and opens a pull request needs a real harness.

Before you trust an agent with real work

  • Is success defined before the run begins?
  • Can the agent find the right project knowledge without loading everything?
  • Does every tool have a clear contract and failure state?
  • Is execution isolated from production systems?
  • Are important decisions stored outside the conversation?
  • Does every risky step have evidence behind it?
  • Are irreversible actions protected by approval?
  • Does every loop have a retry cap and a budget?
  • Can the run resume after an interruption?
  • Can you explain every tool call and state change?
  • Does each failure update a guide, test, tool or policy?
  • Can the final result be rolled back?

If several answers are no, a stronger model won't make the system reliable. It will only make the failure more expensive. Checklist and levels adapted from rari, Harness Engineering.

Case study: an agent-first codebase

OpenAI describes a team that shipped an internal product over five months with no hand-written code: about a million lines and roughly 1,500 merged pull requests, starting with three engineers directing Codex. The engineers' job shifted to designing the environment, stating intent, and building feedback loops.

  • Ask what capability is missing. Early progress was slow because the environment was underspecified, not because the model was weak.
  • Give the agent a map, not a manual. One giant instructions file crowded out the task and went stale. A short entry file (about 100 lines) pointing into a structured docs folder worked better.
  • If the agent can't see it, it doesn't exist. Decisions in chat threads or people's heads are invisible. Put them in versioned files in the repo.
  • Make the app legible. Each change could boot its own instance, and the agent could drive the UI and query its own logs and metrics.
  • Enforce invariants, not implementations. Custom lint rules whose error messages tell the agent how to fix the problem.
  • Clean up continuously. Agents copy existing patterns, bad ones included. Background agents opened small refactoring pull requests on a schedule.

The authors caution that these results depend on heavy investment in that specific repository and shouldn't be assumed to generalize.

From managing agents to enabling them

In a conversation with Greg Isenberg, Allie K. Miller describes running 34 agents led by an AI chief of staff with a layer of directors beneath it. Her framing is that the job shifts from managing agents to enabling them, and that she has moved "from managing to like waiting for escalations." Four ideas from that conversation are worth building on:

Start with one agent, then add layers. A coordinator with a few directors, each owning a domain, scales further than a flat pile of agents.

"Do smart things." Her strongest prompt is three words. The lesson: a short, open instruction only works when the agent already has deep context and clear limits, which is exactly what the harness supplies.

Make everything queryable. A short daily diary captures context that never reaches email or meetings, so agents can find it. The same idea as OpenAI's "if the agent can't see it, it doesn't exist."

Use agents as watchdogs. Point an agent at the others' work to catch duplicated effort and conflicting decisions before they compound.

Hands-on labs

  1. Raw loop. Write a 60-line agent: call the model, run any requested tool, append the result, repeat until done. Set a budget limit from the start.
  2. Three patterns. Summarize five articles three ways (sequential, parallel, loop) and compare time, cost and quality.
  3. Sub-agents. A coordinator splits a research question into three parts, gives each to a sub-agent with its own context, and merges cited results.
  4. Progress file. Have the agent update a progress file after each step. Stop it mid-run and resume from the file.
  5. MCP server. Wrap the Module 3 search as an MCP server and call it from an MCP client.
  6. Limits and approval. Add max steps, a dollar budget and a timeout, plus a confirm step before any risky tool. Show each one trigger.
  7. Failure clinic. Debug a broken agent with seven seeded failures, one per row of the harness table, using only its traces and history log. Fix each and rerun to prove it's gone.
  8. Make a repo agent-legible. Add a short map file and a docs folder (architecture, decisions, active plan) to your RAG repo, plus one lint rule whose error explains the fix. Give a coding agent the same feature request before and after, and count your corrections.
  9. Agent chief of staff. Build a coordinator that reads a daily diary file and each sub-agent's progress file, flags duplicate or conflicting work, and escalates to you only when a judgment call is needed.
Project · Research agent with sub-agents

Given a question, it plans, dispatches sub-agents, and returns a cited report, with limits, a progress file, and a trace of every step.

Done when: it runs from your own loop (a framework is optional afterward), every limit demonstrably stops it, it resumes after interruption, brain, hands and history are separate components, and every run saves its full history plus a change receipt (context sources, tools used, test results, retries, cost and a rollback point).

Watch-out

Agents fail in long, costly loops. Set the budget limit in the first lab, not the last.

Hands-on labs
