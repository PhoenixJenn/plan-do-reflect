AI Beyond Fundamentals

A hands-on course for engineers who can already call a model and want to build AI systems that hold up in production.

Core Skills 8 modules About 14 weeks Try It

Why It Matters

AI Fundamentals teaches you to use AI. This course teaches you to build with it. The gap between a demo that works once and a system people rely on is almost never the model. It is retrieval that finds the right passage, evals that catch regressions, guardrails that stop bad actions, and a harness that keeps an agent on track. Those are engineering skills, and they can be learned by building.

"Humans steer. Agents execute."

OpenAI, Harness engineering

How the Course Works

Every module follows the same loop as the rest of this site. Plan with a short concept lesson. Do three to six guided labs, each with starter code and a checkpoint test. Reflect by shipping a module project and writing down what broke and how you fixed it.

All labs use one shared document collection (public company filings, meeting minutes, or product manuals all work), so you build one system that grows each module instead of seven throwaway demos. You need Python, Git, and comfort calling a REST API. No machine learning background is assumed.

What you'll learn

  • Keeping API keys in environment files, never in code
  • Python environments with uv and a monorepo layout
  • A shared client wrapper that logs tokens, cost and latency for every call

Hands-on labs

  1. Scaffold the repo. One folder per project (chatbot, extraction, RAG, evals, agent, RAG vs fine-tune) plus a shared folder.
  2. Three providers, one prompt. Call Claude, OpenAI and Gemini with the same prompt. Find the token counts in each raw response.
  3. Run a model locally. Install Ollama, pull a small open model, and call it through its OpenAI-compatible endpoint.
  4. Build the logger. Every call appends model, input tokens, output tokens, milliseconds and dollars to a log file. Every later module reuses it.
Checkpoint

A test that calls all four providers and confirms a log row exists for each.

Top

What you'll learn

  • Provider APIs: messages, roles, system prompts, and how request shapes differ
  • Tokens, context windows, and what happens at the limit
  • Sampling settings: temperature, top-p, max tokens, stop sequences
  • Streaming: time to first token versus total latency
  • Cost per call, and why output tokens usually dominate
  • The KV cache inside the model, and prompt caching as providers expose it
  • Semantic caching: return a stored answer when a new question means the same thing
  • Picking a model by trading off quality, speed and cost

Hands-on labs

  1. Token intuition. Guess the token count for English, code, JSON, emoji and Japanese, then check. Discuss why some cost more.
  2. Temperature sweep. Run one prompt 10 times at three temperatures and count how many distinct answers you get.
  3. Streaming vs blocking. Time the same long answer both ways and chart the difference.
  4. Prompt caching. Ask five questions about one long document, with and without caching. Compare cost and latency from your log.
  5. Semantic cache. Test 20 paraphrased questions and find the similarity threshold where wrong answers start slipping through.
Project · Chatbot with a live cost meter

A streaming chat app that shows tokens, dollars and latency per message and a running total, with a model picker that includes one local model.

Done when: cost matches the provider's pricing within 5%, the cache hit rate is visible, and the README compares three models on the same 10 questions.

Hands-on labs

  1. Zero-shot vs few-shot. Sort 50 support tickets into 5 categories with 0, 2 and 5 examples. Compare accuracy.
  2. Schema extraction. Define an invoice model, force schema output, and retry on validation failure. Count retries across 20 documents.
  3. Tool calling by hand. Give the model an exchange-rate tool and a calculator. Log each round trip so the loop is visible.
  4. Grounding. Ask 15 questions about a policy document, half unanswerable. Count invented answers with and without a "quote or say not found" rule.
  5. Prompt versions. Store prompts as files, run two versions on the same inputs, and produce a results table.
Project · Invoice PDF to clean JSON

A command-line tool that turns 20 varied invoices into schema-valid JSON, with an arithmetic check that line items add up to the total.

Done when: every output passes the schema, field accuracy is reported against a hand-labeled answer key, and two prompt versions are compared with numbers.

Watch-out

Advice on reasoning prompts differs by model family. Teach learners to test it on their own task rather than memorize a rule.

Top

Retrieval-augmented generation (RAG) has two halves. Documents are processed once and stored in an index. Every question then runs through search, and the best passages are handed to the model along with the question.

What you'll learn

  • Digitizing documents: OCR for scans, text extraction for native PDFs
  • Layout parsing that keeps tables, headers and reading order intact
  • Chunking strategy per document type, including chunk size and overlap
  • Vector indexes: HNSW (fast and accurate, memory-heavy), IVF (clustered, cheaper at scale), PQ (compressed, smaller and less exact)
  • Hybrid search: keyword scores (BM25) plus vector scores, merged
  • Splitting multi-part questions and filtering by metadata such as date or source
  • Reranking, then measuring retrieval with recall@k against labeled questions

Hands-on labs

  1. Naive baseline. Build the simplest RAG over the course documents. Write 30 questions with the correct source page and record recall@5. Every later lab has to beat it.
  2. Parsing bake-off. Extract 5 hard PDFs (one scanned, two table-heavy) with a basic extractor and a layout-aware parser. Note what each one lost.
  3. Chunking experiment. Compare three chunking strategies on the same 30 questions.
  4. Index types. Build HNSW and IVF-PQ indexes on 100,000 synthetic vectors. Measure build time, memory, speed and recall.
  5. Hybrid search. Add keyword search and fuse the results. Find the questions it fixes, usually exact terms like IDs and product codes.
  6. Rerank and filter. Retrieve 20, rerank to 5, and add a metadata filter. Record final recall and the added latency.
Project · Chat with 100 messy PDFs

A deployed chat app with citations that link to the source page, a semantic cache, and a page showing recall before and after each upgrade.

Done when: citations open the right page, recall beats the baseline with the biggest win identified, and cost and latency per question are reported.

Watch-out

This is the longest module. Most retrieval failures start at parsing, not embeddings, so finish labs 1 to 3 before tuning search.

Top

What you'll learn

  • Golden sets: real user questions with expected answers, kept fresh
  • Grading methods: exact match, code checks, an LLM judge with a rubric, human spot checks
  • Calibrating the judge against your own labels before trusting it
  • RAG metrics (RAGAS): faithfulness, answer relevance, context precision, context recall
  • Tracing every call, retrieval and tool step (Langfuse, LangSmith)
  • Input guardrails (personal data, prompt injection, off-topic) and output guardrails (schema, unsupported claims)
  • Token budgets, cost alerts, and regression tests on every change

Hands-on labs

  1. Golden set. Turn the Module 3 questions into a 50-item set, including 10 the documents can't answer.
  2. LLM as judge. Hand-grade 20 answers on a 1 to 5 faithfulness rubric, run the judge on the same 20, and report agreement.
  3. RAGAS. Score the Module 3 app on all four metrics and find the weakest.
  4. Tracing. Instrument the app and find the slowest step across 10 requests.
  5. Guardrails. Redact personal data on input and require every claim to cite a passage on output. Try 10 attack prompts and count what gets through.
  6. Budget alert. Add a daily token cap per user and an alert when spend crosses a threshold.
Project · Eval suite that runs in CI

A GitHub Actions workflow that runs the golden set on every pull request, posts scores as a comment, and fails the build if quality drops past a set margin.

Done when: a deliberately broken prompt fails the build, judge agreement is reported, and each eval run stays under a stated budget.

Watch-out

LLM judges drift and tend to favor longer answers. Teach calibration before automation.

Harness engineering: fix the system, not the prompt

When an agent fails, the instinct is to rewrite the prompt, switch models, or add context. The failures usually come back. The better move is to name the failure and change the harness.

Failure you seeHarness fix
Missing contextGive the agent a map of its workspace or a retrieval rule
Wrong toolImprove the tool description or add routing
Bad outputAdd a validator or a stricter output contract
Repeated loopCap retries and escalate to a human
Unsafe actionAdd a permission gate
Lost decisionWrite it to durable state
Unknown failureAdd tracing and capture evidence

Adapted from rari, Harness Engineering.

Brain. The model that reasons. It should not also be the filesystem, the permission system, the memory store and the audit log.

Hands. The sandbox and tools that act, each behind its own permissions.

History. An append-only record of what happened. Keep the whole run, not only the final answer. It is what makes debugging and evals possible.

Case study: an agent-first codebase

OpenAI describes a team that shipped an internal product over five months with no hand-written code: about a million lines and roughly 1,500 merged pull requests, starting with three engineers directing Codex. The engineers' job shifted to designing the environment, stating intent, and building feedback loops.

  • Ask what capability is missing. Early progress was slow because the environment was underspecified, not because the model was weak.
  • Give the agent a map, not a manual. One giant instructions file crowded out the task and went stale. A short entry file (about 100 lines) pointing into a structured docs folder worked better.
  • If the agent can't see it, it doesn't exist. Decisions in chat threads or people's heads are invisible. Put them in versioned files in the repo.
  • Make the app legible. Each change could boot its own instance, and the agent could drive the UI and query its own logs and metrics.
  • Enforce invariants, not implementations. Custom lint rules whose error messages tell the agent how to fix the problem.
  • Clean up continuously. Agents copy existing patterns, bad ones included. Background agents opened small refactoring pull requests on a schedule.

The authors caution that these results depend on heavy investment in that specific repository and shouldn't be assumed to generalize.

From managing agents to enabling them

In a conversation with Greg Isenberg, Allie K. Miller describes running 34 agents led by an AI chief of staff with a layer of directors beneath it. Her framing is that the job shifts from managing agents to enabling them, and that she has moved "from managing to like waiting for escalations." Four ideas from that conversation translate directly into course material:

Start with one agent, then add layers. A coordinator with a few directors, each owning a domain, scales further than a flat pile of agents.

"Do smart things." Her strongest prompt is three words. The lesson for learners: a short, open instruction only works when the agent already has deep context and clear limits, which is exactly what the harness supplies.

Make everything queryable. A short daily diary captures context that never reaches email or meetings, so agents can find it. The same idea as OpenAI's "if the agent can't see it, it doesn't exist."

Use agents as watchdogs. Point an agent at the others' work to catch duplicated effort and conflicting decisions before they compound.

Hands-on labs

  1. Raw loop. Write a 60-line agent: call the model, run any requested tool, append the result, repeat until done. Set a budget limit from the start.
  2. Three patterns. Summarize five articles three ways (sequential, parallel, loop) and compare time, cost and quality.
  3. Sub-agents. A coordinator splits a research question into three parts, gives each to a sub-agent with its own context, and merges cited results.
  4. Progress file. Have the agent update a progress file after each step. Stop it mid-run and resume from the file.
  5. MCP server. Wrap the Module 3 search as an MCP server and call it from an MCP client.
  6. Limits and approval. Add max steps, a dollar budget and a timeout, plus a confirm step before any risky tool. Show each one trigger.
  7. Failure clinic. Debug a broken agent with seven seeded failures, one per row of the harness table, using only its traces and history log. Fix each and rerun to prove it's gone.
  8. Make a repo agent-legible. Add a short map file and a docs folder (architecture, decisions, active plan) to your RAG repo, plus one lint rule whose error explains the fix. Give a coding agent the same feature request before and after, and count your corrections.
  9. Agent chief of staff. Build a coordinator that reads a daily diary file and each sub-agent's progress file, flags duplicate or conflicting work, and escalates to you only when a judgment call is needed.
Project · Research agent with sub-agents

Given a question, it plans, dispatches sub-agents, and returns a cited report, with limits, a progress file, and a trace of every step.

Done when: it runs from your own loop (a framework is optional afterward), every limit demonstrably stops it, it resumes after interruption, brain, hands and history are separate components, and the full history is saved with each run.

Hands-on labs

  1. Router. A small model labels requests easy or hard and sends hard ones to a large model. Compare cost and quality to always using the large one.
  2. Injection red team. Plant hidden instructions in a document in your RAG collection and try to make the app leak its instructions or misuse a tool. Add defenses and retest.
  3. Replace the LLM. Find one model step from an earlier project that a rule could handle. Measure both.
  4. Design doc. Write a one-page decision record with latency, cost and quality targets.
Project · RAG vs fine-tune, same task

Build one task both ways: RAG, and a fine-tuned small open model (or a hosted fine-tuning service). Run both through your Module 4 evals.

Done when: both use the same eval set, a table compares quality, cost, latency and effort to update, and the recommendation follows from the numbers.

Requirements

  • A real problem someone actually has, not a tutorial
  • Raw API and your own loop first; a framework only if the README explains what it replaced
  • A RAG app and an agent app, both deployed
  • A README with the architecture, eval scores, cost per request and latency numbers
  • A 60-second demo video
  • A short write-up of what broke and how you fixed it

Hands-on labs

  1. Problem pitch. One paragraph: the user, the problem, why an LLM helps, and how you'll measure success. Get feedback before building.
  2. README first. Fill in the architecture, eval, cost and latency sections before writing code.
  3. Deploy. Secrets in environment variables, a health check, and rate limiting.
  4. Demo and postmortem. Record the video and write a blameless what-broke review.
